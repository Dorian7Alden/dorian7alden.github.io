## 阶段一：锁与并发控制

这是 tpmC 的第一道天花板，TPC-C 在仓库数 < 并发数时，Warehouse/District 热点行更新会成为锁竞争爆炸点【turn2search3】。

**1. 锁管理器分片化**
- 手段：按 `(table_id, page_id, slot_id)` 计算 hash，映射到 N 个独立 shard，每个 shard 自带 mutex + lock hash table。shard 数量取 CPU 物理核数的 2~4 倍。
- 实现要点：锁对象（lock_t）从对象池预分配，acquire/release 只做链表指针操作，禁止在临界区内 malloc；每个 shard 的 mutex 用 `alignas(64)` padding 隔离，避免 false sharing【turn0search0】【turn2search8】。
- 一致性保障：2PL 协议本身不变，只是把"谁负责管理某个锁"做了路由分片，逻辑等价于一个全局锁表，可串行性不受影响。

**2. 死锁预防策略选择与切换**
- Wait-Die（非抢占，老等新、新被 abort）适合中等争用；Wound-Wait（抢占，老 wound 新）适合高争用且希望老事务优先完成；NO-Wait 适合极低争用，abort-rate 会升高但无死锁检测开销【turn1search17】【turn1search18】。
- 落地建议：默认 Wound-Wait（abort 数更少），同时维护一个 wait-for 图做轻量级 DL_DETECT 作为兜底；当检测到 lock thrashing（平均锁等待队列长度超阈值）时自动切到 NO-Wait 模式【turn2search3】。
- 一致性保障：三种策略都保证可串行化，区别仅在 abort 哪个事务，不影响正确性。abort 的事务必须完整回滚（undo 全部修改）才能保证一致性。

**3. 锁粒度与持有时间**
- 行级锁优先于页级锁；表访问用意向锁（IS/IX）避免表锁阻塞。
- TPC-C 的 `Warehouse.W_YTD` 和 `District.D_YTD` 是支付事务的写热点。可考虑把 YTD 拆为多个子账户（如 10 个 sub-YTD），Payment 事务按 `w_id % 10` 选子账户更新，把单行热点打散为 10 行——这是逻辑层优化，不影响总额一致性（子账户之和 = 原 YTD）。
- 缩短锁持有时间：commit 阶段释放所有行锁后再做后续清理（如统计、日志归档）；统计更新移出锁临界区，用 atomic counter 异步累加。

**4. latch 与 lock 严格分离**
- latch 保护物理结构（page、index node），微秒级持有，无死锁检测；lock 保护逻辑事务隔离，毫秒到秒级持有，有死锁处理。
- 落地：latch 用 `std::atomic` 或 spinlock + backoff；lock 走锁管理器。**严禁用 latch 代替 lock**——一旦 latch 持有跨越 IO 或事务等待，会引发优先级反转与系统级卡顿。

## 阶段二：存储与 WAL 落盘

锁瓶颈消除后，fsync 串行化是第二道天花板。这一阶段的所有优化都必须死守"WAL 先行"原则：数据页落盘前，对应 redo log 必须已 fsync 成功【turn2search19】。

**1. Group Commit 三阶段流水线**
- 经典实现（MySQL Binlog Group Commit）：FLUSH_STAGE → SYNC_STAGE → COMMIT_STAGE，每阶段一个队列，阶段间可并发【turn2search12】【turn2search22】。
  - FLUSH：leader 线程把队列中所有事务的 redo 写入 WAL buffer（内存操作）
  - SYNC：leader 执行一次 fsync，所有 follower 阻塞等待
  - COMMIT：leader 通知所有 follower 提交完成，各自释放锁
- 批次触发：时间阈值（200μs~1ms）或数量阈值（16~64 个事务），先到先触发。
- 一致性保障：fsync 在 COMMIT 阶段之前完成，事务对外可见时 redo 已落盘；崩溃恢复时未 fsync 的事务自动回滚，不破坏持久性。

**2. Commit Pipeline 异步化**
- MatrixOne 的做法：事务进入 pipeline 前并发更新 memtable（不阻塞彼此），pipeline 内异步持久化 WAL entry，多个 entry 的 fsync 时间窗口可重叠【turn2search27】。
- 关键设计：WAL entry 落盘前，事务状态保持"pre-commit"，对外不可见；落盘后批量置为"committed"并唤醒等待该事务的读请求。
- 一致性保障：pre-commit 状态在崩溃恢复时按未提交处理（回滚），committed 状态才重放——这等价于把 fsync 从事务关键路径上摘除，但保留持久性语义。

**3. 并行 redo / 多 log stream**
- WAL buffer 按 `txn_id % N` 或 `(table_id, partition_id)` hash 到 N 个 log stream，每个 stream 独立 writer 线程并发 fsync。
- 全局 LSN 维护跨 stream 顺序：每个 log entry 记录 `(stream_id, local_lsn, global_lsn)`，恢复时按 global_lsn 归并重放。
- 一致性保障：单事务的 redo 必须落在同一 stream 内保证局部有序；跨事务的串行化序由 global_lsn 决定，恢复时严格按 global_lsn 重放即可保证可串行性。
- 注意：RocksDB 的新方案 even 做到 leaderless write path——双 buffer ping-pong，fsync 在 mutex 外执行，新 writer 可并发追加到另一个 buffer【turn0search10】。

**4. fsync 与文件层优化**
- 用 `fdatasync()` 替代 `fsync()`：不刷文件元数据（修改时间等），减少一次元数据 IO【turn2search23】。
- WAL 文件用 `fallocate()` 预分配固定大小（如 1GB），避免运行时 extend 触发文件系统锁与碎片。
- WAL 文件轮转：多个 WAL 文件循环使用，单文件写满切换下一个，避免单文件的 inode 锁竞争。
- 若 Buffer Pool 自管缓存，可对 WAL 文件开 `O_DIRECT` 绕过 page cache，减少一次内存拷贝。

**5. Checkpoint 优化**
- Fuzzy Checkpoint：checkpoint 过程不阻塞事务读写，记录 checkpoint LSN 时允许并发修改。
- 增量刷脏：后台 flush 线程持续把脏页写回，控制脏页比例在 75%~85%，避免 checkpoint 时批量刷盘造成延迟尖刺。
- 一致性保障：checkpoint LSN 之前的 WAL 可裁剪；恢复时从最近 checkpoint LSN 开始重放 redo，之后应用 undo 回滚未提交事务——这是标准 ARIES 协议，不因 fuzzy 化而改变。

## 阶段三：Buffer Pool 与内存

IO 串行化解决后，缓存命中率与内存带宽成为瓶颈。TPC-C 单事务可能触发数十次 page read，命中率每降 1% 都拖累 tpmC。

**1. 多级分片 Buffer Pool**
- 按 `page_id % N` 分片到 N 个 instance，每个 instance 独立 LRU + free list + flush list + mutex。N = CPU 物理核数。
- 前台线程 fetch page 时只锁对应 instance，不影响其它 instance 的并发访问。
- 一致性保障：pin/unpin 协议不变，page 内容正确性由 WAL + pin 计数保证；分片只是把访问路径拆开。

**2. 替换策略升级**
- LRU-K（K=2）：跟踪每个 page 最近 2 次访问时间，按"第 K 次距今时间"淘汰，能区分"偶尔被扫一次"和"真正热点"，避免全表扫描污染【turn0search20】【turn0search21】。
- 冷热分区：LRU 链表分为 new sublist（热，占 3/8）和 old sublist（冷，占 5/8），新载入 page 先进 old，被第二次访问才晋升 new——这是 InnoDB 的做法【turn0search24】。
- 一致性保障：替换策略只决定"哪个 page 被淘汰"，被淘汰的脏页必须先刷盘（WAL 先行），不影响数据正确性。

**3. NUMA 感知**
- Buffer Pool 按 NUMA 节点分区，每个节点管自己的 page 池；线程优先从本节点 instance 取 page。
- 内存分配用 `numa_alloc_onnode` 或 `mmap + MPOL_BIND`；线程用 `numa_run_on_node` 绑核。
- openGauss MOT 的做法：每表行、每索引节点独立内存池，从本地 NUMA 节点以 2MB chunk 分配，事务内存分配始终 NUMA-local【turn1search32】。
- 一致性保障：NUMA 只影响访问延迟与带宽，page 内容一致性不变。

**4. 大页**
- 显式 hugepage（2MB）分配 Buffer Pool 大块内存，减少 TLB miss。PostgreSQL/MySQL 实测可提升 5%~30% 吞吐【turn3search0】【turn3search2】。
- 落地：`mmap(..., MAP_HUGETLB)` 或预留 `/proc/sys/vm/nr_hugepages` 后 `shmget`。
- 注意：若 max-rss-gb 敏感，关闭 THP（透明大页），改用显式大页——THP 可能导致 RSS 膨胀【turn3search4】。

**5. 异步预读与后台刷盘**
- 顺序访问检测：连续 page 读取超过阈值（如 8 页）触发异步预读，用 `readahead` 或自管 IO 线程批量加载。
- 后台 flush：独立 flush 线程按 dirty page ratio 与 redo 生成速率动态刷盘，避免前台事务同步刷脏。
- 一致性保障：预读只是提前载入，page pin 协议不变；后台刷盘前对应 WAL 必须已 fsync。

## 阶段四：索引与查询路径

TPC-C 的 New-Order 每次插入涉及多表索引更新，Payment 涉及主键查找，索引并发性能直接影响 tpmC。

**1. B+ 树乐观 latch（OLFIT）**
- 读操作无锁化：读版本号 → 读 node 内容 → 再读版本号，两次一致则成功；不一致则重试【turn0search5】【turn0search6】。
- 写操作：持写锁修改，完成后版本号 +1，使并发读者检测到变化而重试。
- 内部节点全程乐观读，只在叶子节点加写锁——根节点不再成为热点。
- 一致性保障：版本号验证保证读者看到一致的 node 快照；SMO（split/merge）期间仍持悲观锁，保证树结构完整性。

**2. latch crabbing 优化**
- 乐观 crabbing：插入/删除时先一路读锁下探到叶子，若叶子"安全"（不会触发 split/merge）则只加叶子写锁完成操作；不安全才回退到悲观 crabbing（全程写锁）【turn2search38】【turn2search40】。
- SMO 自底向上：split 时先加叶子写锁，再向上逐层加父节点写锁，缩短上层持锁时间（PolarDB PolarIndex 2.0 的做法）【turn2search30】。
- 一致性保障：crabbing 保证任意时刻至少持有一个父节点 latch，树结构修改不会让并发遍历者读到不一致指针；安全节点判断确保 split/merge 不会中途失控。

**3. 覆盖索引与索引下推**
- TPC-C Order-Status 事务按 `(w_id, d_id, c_id)` 查询客户最近订单，建覆盖索引把 `o_id, o_carrier_id, o_entry_d` 纳入索引，避免回表。
- 把 WHERE 条件下推到索引扫描层（Index Condition Pushdown），在索引层就过滤掉不满足条件的行，减少回表次数。
- 一致性保障：二级索引与主表由同一事务同步维护，索引内容是数据的子集投影，不影响一致性。

**4. 执行计划缓存**
- PreparedStatement 缓存 parse + optimize 结果，后续相同模板 SQL 直接复用 plan，省去 parser 与优化器开销。
- TPC-C 事务由固定模板 SQL 组成，缓存命中率接近 100%。PolarDB 打榜时这块省了大量 CPU【turn2search30】。
- 一致性保障：缓存的是执行计划（算子树），事务语义（隔离级别、锁、MVCC 可见性）在执行时动态应用，不受缓存影响。

## 阶段五：事务管理与 MVCC

事务系统本身的全局数据结构（活跃事务表、时间戳分配器）在多核下也会成为瓶颈。

**1. 时间戳批量分配**
- 全局 timestamp oracle 每次分配一段（如 1000 个 TS），用完再申请，避免每次事务 start 都走全局原子操作【turn1search10】。
- 单机场景：用 `std::atomic<uint64_t>::fetch_add(batch_size)` 一次取一批，本地线程内分发。
- 一致性保障：TS 单调递增保证可串行化序；批量分配不改变 TS 的全序性质，只是减少争用。

**2. MVCC 版本链与可见性**
- 每个元组维护版本链（undo log 或 inline version），记录 `txn_id, commit_ts, prev_version_ptr`。
- 可见性判断：读事务以自己的 `start_ts` 为快照，只看 `commit_ts <= start_ts` 的版本。
- 版本链头指针更新用 CAS，写事务追加新版本时不阻塞读事务。
- 一致性保障：MVCC 保证读不阻塞写、写不阻塞读，隔离级别由快照定义决定（SI/SSI）；commit_ts 在事务提交时原子写入，保证可见性的原子切换。

**3. 垃圾回收（GC）安全点**
- 维护全局 `min_active_txn_ts`（最老活跃事务的 start_ts），所有 `commit_ts < min_active_txn_ts` 的旧版本可安全回收【turn0search15】【turn0search16】。
- GC 线程周期性扫描版本链，回收不可见版本占用的内存。
- 一致性保障：只回收"没有任何活跃事务可能看到"的版本，等价于一个全局 quiescent point，不影响任何事务的快照视图。SAP HANA 的 hybrid GC、TB-Collect 都是类似思路【turn0search17】【turn0search18】。

**4. OCC / 2PL 混合**
- 低争用事务用 OCC（读时不加锁，commit 时验证写集）；高争用事务回退 2PL。
- 验证阶段：检查写集中每个 key 的版本号是否与读时一致，不一致则 abort。
- 一致性保障：OCC 在 commit 时原子验证，冲突事务必须 abort 并完整回滚，保证可串行化；混合策略只是按负载特征选协议，不改变隔离性保证。

**5. Savepoint 与部分回滚**
- 事务内设置 savepoint，冲突时只回滚到 savepoint 而非整事务回滚，减少 abort 开销。
- TPC-C 中 New-Order 的 1% 远程仓库事务可能因库存不足 abort，用 savepoint 可避免整事务重做。
- 一致性保障：savepoint 回滚只撤销该段修改，已提交部分不变，原子性仍由 undo log 保证。

## 阶段六：CPU 微优化与系统调优

前三阶段把宏观瓶颈打通后，这一阶段压榨单核效率，收益相对小但累积可观。

**1. cache line 对齐与 false sharing 消除**
- 热点共享结构（锁管理器 shard mutex、全局计数器、事务表头）用 `alignas(64)` 对齐到 cache line，避免多核修改同一 line 触发 bouncing【turn3search15】【turn3search19】。
- 每 shard mutex 后补 padding：`struct Shard { alignas(64) std::mutex m; char pad[64 - sizeof(std::mutex)]; ... };`
- 一致性保障：只影响缓存效率，不改变语义。

**2. 无锁数据结构 + Epoch-Based Reclamation**
- 读多写少的全局结构（如统计计数器、连接表）用 lock-free 实现；内存回收用 EBR：每个线程进入/退出临界区时刷新 epoch，旧节点延迟 3 个 epoch 后回收【turn2search25】【turn2search27】【turn2search28】。
- 一致性保障：lock-free 结构保证 linearizability；EBR 保证回收时无任何线程持有该节点引用，不会 use-after-free。

**3. 绑核与 NUMA 调度**
- `numactl --cpunodebind=N --membind=N` 绑定数据库进程到特定 NUMA 节点；IO 中断也可用 `irqbalance` 或手动 `/proc/irq/*/smp_affinity` 绑到本地 CPU。
- 一致性保障：纯调度优化，不影响正确性。

**4. 编译优化（LTO + PGO）**
- LTO（链接时优化）：跨编译单元内联与死代码消除，Clang/GCC 用 `-flto=thin`。
- PGO（运行时反馈优化）：先用 TPC-C 典型负载跑一遍生成 profile，再重新编译让编译器基于真实分支概率优化，实测 MySQL 用 LTO+PGO 提升高达 85%【turn2search19】【turn2search18】。
- 落地：`-fprofile-generate` → 跑 BenchmarkSQL → `-fprofile-use` 重新编译。
- 一致性保障：只影响代码生成质量，不改变语义。

**5. 内核与文件系统参数**
- IO 调度器设为 `none`/`noop`（SSD/NVMe 场景，减少 CPU 开销）。
- 文件系统（XFS）：mount 选项 `noatime,nodiratime`；mkfs 时条带大小对齐数据库 page size。
- `vm.swappiness=1` 几乎禁止 swap，避免数据库内存被换出导致延迟尖刺。
- 若 max-rss-gb 敏感：关闭 THP（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`），改用显式大页【turn3search4】。
- 一致性保障：系统参数调优不改变数据库协议语义；关闭 THP 唯一影响是 TLB 效率，不影响数据正确性。

## 推荐落地优先级清单

按"投入产出比 + 风险可控性"排序，建议按以下顺序逐项落地，每项做完回归 tpmC/abort-rate/max-rss 三指标：

1. **锁管理器分片化**（阶段一）— 通常 tpmC 直接翻倍，风险低
2. **Group Commit 三阶段流水线**（阶段二）— fsync 次数骤降，tpmC 显著提升
3. **B+ 树乐观 latch OLFIT**（阶段四）— 消除索引根节点热点
4. **多级分片 Buffer Pool + LRU-K**（阶段三）— 命中率提升 + latch 争用下降
5. **MVCC 时间戳批量分配 + GC 安全点**（阶段五）— abort-rate 下降，RSS 稳定
6. **Commit Pipeline 异步化**（阶段二）— 进一步压榨提交路径
7. **NUMA 感知 + 大页**（阶段三）— 多路服务器收益巨大
8. **死锁预防策略切换 + 热点行分解**（阶段一）— 降 abort-rate
9. **执行计划缓存**（阶段四）— 降 CPU
10. **LTO + PGO + cache line 对齐**（阶段六）— 锦上添花

每一项优化后必须用同一基线回归验证：tpmC 不降、abort-rate 不升、max-rss 不膨胀，且 crash recovery 测试（kill -9 后重启）能正确恢复到一致状态——这是"一致性必须通过"的硬性验收标准。
