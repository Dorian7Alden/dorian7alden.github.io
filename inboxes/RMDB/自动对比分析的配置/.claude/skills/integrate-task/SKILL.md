# integrate-task

## 定位

此 skill 在每题首次集成时激活一次。分析完成后自动进入代码实现，用户直接提测，无需手动编码。

**核心原则：题目 1-N 的累计规格是唯一正确标准，满分分支仅供参考，测试是验证手段。**

## 执行架构

你是**协调者**，不亲自做深度分析。每个分析阶段派发**独立 sub-agent**，每个 sub-agent 拥有**干净独立的上下文**，只接收该阶段必需的数据，不传主对话历史。

```
你（协调者）
  ├──派发──→ sub-agent-1（需求加载 / Explore）
  ├──派发──→ sub-agent-2（模块映射 / Explore）
  ├──派发──→ sub-agent-3（差异分析 / Explore + worktree）
  ├──派发──→ sub-agent-4a（测试编写 / general-purpose）
  │   ├──并行──→ sub-agent-4b（当前分支运行 / general-purpose）
  │   └──并行──→ sub-agent-4c（满分分支运行 / general-purpose + worktree）
  │   └──派发──→ sub-agent-4d（对比分析 / code-reviewer）
  ├──派发──→ sub-agent-5（冲突检测 / code-reviewer）
  ├──合成──→ 阶段 6 分析报告（你执行）
  ├──派发──→ sub-agent-7（独立审核 / code-reviewer + 全新上下文）
  │   └──整合审核意见 → 最终报告
  └──派发──→ sub-agent-8（代码实现 / general-purpose）
              └── 按报告编码、编译、测试，不提交
```

## Sub-agent 派发规则

1. 每个分析阶段至少派发 1 个独立 sub-agent
2. Sub-agent prompt 只包含该阶段必需的输入数据（题目编号、文件路径、模块列表等），**不传主对话历史**
3. 有依赖的阶段（如阶段 5 需要阶段 3、4 产出），传递上游阶段的结果摘要，不传完整对话
4. 独立分析任务并行派发（如阶段 4.2 的两个分支测试）
5. Sub-agent 分析阶段（1-7）不修改代码，实现阶段（8）可修改代码但不提交
6. 满分分支相关的 sub-agent 必须在 git worktree 中运行
7. Sub-agent 类型：Explore（阶段 1、2、3）、general-purpose（阶段 4.1、4.2、8）、code-reviewer（阶段 4.3、5、7）

## 八阶段工作流

```
阶段 1：需求加载 → 阶段 2：模块映射 → 阶段 3：差异分析
                                            ↓
阶段 8：代码实现 ← 阶段 7：独立审核 ← 阶段 6：分析报告 ← 阶段 5：冲突检测 ← 阶段 4：测试验证
```

---

### 阶段 1：需求加载

派发 **1 个 Explore sub-agent**。

**Agent prompt 必须包含：**
- 当前题目编号（如 T03）
- `docs/tasks/task-XX-*.md` 路径（当前题 + 全部前序题文档路径）
- CLAUDE.md 中满分分支对照表
- 指令：提取接口签名、测试用例（SQL + 期望输出）、输出格式要求、约束条件。汇总前序题行为清单。

**Agent 必须返回：**
- 当前题目要求清单（接口签名、测试用例、输出格式、约束）
- 前序题行为清单（已承诺的全部输出格式和行为语义）
- 满分分支名称

你只接收结果，不做分析。

---

### 阶段 2：模块映射

派发 **1 个 Explore sub-agent**。

**Agent prompt 必须包含：**
- 阶段 1 返回的接口签名列表
- `src/` 目录结构和各模块 README 路径
- 指令：定位涉及的 src/ 子目录和关键文件，标注共享模块（被前序题使用）vs 新增模块

**Agent 必须返回：**
- 涉及的 src/ 子目录和关键文件
- 模块分类（共享模块 vs 新增模块）
- 会被触碰的函数/类/接口清单

你只接收结果，不做分析。

---

### 阶段 3：差异分析

**你需要先执行：**
```bash
# 创建满分分支的隔离 worktree
git worktree add /tmp/fullscore-<task> <满分分支名>
```

然后派发 **1 个 Explore sub-agent**。

**Agent prompt 必须包含：**
- 阶段 2 的模块和接口清单
- 满分分支 worktree 路径（/tmp/fullscore-<task>）
- 当前分支路径（项目根目录）
- 指令：对比每个函数/接口，分级为关键差异（影响题目要求的输入输出行为）vs 非关键差异（纯策略/性能差异）。只关注关键差异。

**Agent 必须返回：**
- 关键差异列表（每个差异的具体描述和潜在影响）
- 非关键差异摘要

完成后清理 worktree：`git worktree remove /tmp/fullscore-<task> --force`

你只接收结果，不做分析。

---

### 阶段 4：测试验证

#### 4.1 编写测试

派发 **1 个 general-purpose sub-agent**。

**Agent prompt 必须包含：**
- 阶段 1 的当前题目所有测试用例（SQL 输入 + 期望输出）
- 输出格式要求
- 当前分支的测试基础设施（test/ 目录结构、CMakeLists.txt）
- 指令：为每个测试点编写可执行的测试用例，覆盖每个输出点

**Agent 必须返回：**
- 测试文件列表（已写入的文件路径）
- 运行指令（如 `cd build && make unit_test && ./bin/unit_test`）

#### 4.2 交叉验证

**并行**派发 **2 个 general-purpose sub-agent**：
- Agent A：在当前分支编译并运行阶段 4.1 的测试，返回结果
- Agent B：在满分分支 worktree 中编译并运行同一测试，返回结果

然后派发 **1 个 code-reviewer sub-agent** 做对比分析。

**Agent prompt 必须包含：**
- 两个分支的测试输出
- 阶段 1 的全部题目要求（当前题 + 前序题）
- 指令：先看结果是否一致。一致的跳过。不一致的进入分析模式，以 T01-TN 累计规格为准绳做取舍判断。

**Agent 必须返回对比结论**，格式：
```
### 测试点 N：<名称>
- 一致性：一致 / 不一致
- 不一致分析：（各自符合/不符合题目哪里）
- 取舍结论：<结论 + 以题目要求为支撑的理由>
```

注意事项：
- **不能盲从满分分支**
- **必须引用题目文档原文支撑结论**
- 判断标准层级：题目 1-N 累计规格 > 单个满分分支行为

---

### 阶段 5：冲突检测

派发 **1 个 code-reviewer sub-agent**。

**Agent prompt 必须包含：**
- 阶段 1 的前序题行为清单
- 阶段 3 的关键差异列表
- 阶段 4 的测试对比结论
- 指令：逐项判定每个差异点是否影响前序题的输出行为，分类为 安全 / 冲突

**Agent 必须返回：**
```
### 冲突 N：<简述>
- 涉及前序题：T0X
- 前序题行为承诺：（引用）
- 当前题目需要的改动：
- 冲突点：
- 解决方案：
```

你只接收结果，不做分析。

---

### 阶段 6：分析报告（实现指南）

**此阶段由你（主模型）执行**，不再派发 sub-agent。

合成阶段 1-5 所有 sub-agent 的返回结果，输出以下格式的报告。报告必须可直接指导编码。

#### 报告模板

```markdown
# T0X <题目名称> 集成分析报告

## 一、题目概览
- 题目编号：T0X
- 名称：<名称>
- 满分分支：<分支名>
- 核心要求：（一段话摘要）
- 前序依赖：T01-T0(X-1)

## 二、模块与接口清单

| 模块路径 | 关键文件 | 函数/接口 | 类型 | 当前状态 | 题目要求 |
|---------|---------|----------|------|---------|---------|
| src/xxx/ | xxx.cpp | method() | 共享 | 已实现 | <引用> |

## 三、差异明细

### 差异 1：<简述>
- **文件**：src/xxx/xxx.cpp
- **函数/位置**：ClassName::methodName()，行 L1-L2
- **题目要求**：（引用题目文档原文）
- **当前分支现状**：（具体描述）
- **满分分支做法**：（具体描述）
- **分析**：当前分支 → 符合 T0X 的 Y 要求，但... / 满分分支 → 符合 Z 要求，但...
- **取舍结论**：<明确选哪个 + 引用题目要求支撑>
- **实现方向**：（具体的实现路径描述）

### 差异 2：...

## 四、测试差距明细

### 测试点 1：<名称>
- **题目要求原文**：（引用）
- **SQL 输入**：...
- **期望输出**：...
- **当前分支实际输出**：...
- **满分分支实际输出**：...
- **一致性判断**：一致 / 不一致
- **不一致分析**：...
- **结论**：当前分支需要调整到 <具体目标>

## 五、冲突明细

### 冲突 1：<简述>
- **涉及前序题**：T0X
- **前序题行为承诺**：（引用）
- **当前题目需要的改动**：<具体改动>
- **冲突点**：...
- **解决方案**：...

## 六、实现清单

| 优先级 | 文件 | 函数/位置 | 改动概要 | 关联差异 | 风险 |
|--------|------|----------|---------|---------|------|
| P0 | ... | ... | ... | 差异 N | 高 |

## 七、独立审核结果

（阶段 7 完成后填入）

## 八、实现结果

（阶段 8 完成后填入：修改文件列表、编译结果、测试结果）
```

报告输出后进入阶段 7。

---

### 阶段 7：独立审核（复现验证）

派发 **1 个全新的 code-reviewer sub-agent**。

**⚠️ 此 Agent 不接受任何前序阶段的上下文。** Agent prompt 只包含：
- 阶段 6 的完整分析报告
- 当前题目编号
- 项目根目录路径

**审核员分两步工作：**

**第一步：逐条复现验证**

审核员以报告的每条结论为线索，去原始材料中验证，如同论文审稿照引用查原始文献：
- 报告说某处有差异 → 打开对应文件，查看代码，确认差异是否存在、报告描述是否准确
- 报告引用了某条题目要求 → 打开题目文档，确认引用是否准确、有无断章取义
- 报告给出了取舍结论 → 结合累加的前序题要求，独立判断取舍是否成立
- 报告标记了冲突 → 验证冲突是否真实存在，解决方案是否可行
- 报告声称了测试输出 → 核对题目期望输出，确认结论正确

**第二步：逻辑推演**

针对题目文档中的关键测试用例，在逻辑层面模拟执行流程：
- 从 SQL 输入开始，逐步推演：解析 → 语义检查 → 优化 → 计划生成 → 算子执行 → 最终输出
- 在每个阶段，基于报告建议的实现方向，推理"当前阶段会产生什么中间结果"
- 检查推理结果是否能走到题目要求的期望输出
- 对多分支场景（条件判断、并发调度），推演所有路径

**审核员必须返回：**

```markdown
# 独立审核报告

## 已确认
- [x] <逐条列出复现验证通过的项>

## 存疑
- [ ] <验证不通过的项>
  - 审核员在原始材料中看到：...
  - 报告说：...
  - 分歧点：...

## 遗漏
- <题目要求中明确存在但报告未覆盖的点>

## 推演记录
### 测试用例 X 逻辑推演
1. 解析阶段：... → 预期：... → 实际推演：...
2. 语义检查：... → ...
3. 优化/计划生成：... → ...
4. 算子执行：... → ...
5. 最终输出：... → 与期望输出对比：一致 / 断裂
```

**审核员不从任何前序 sub-agent 的结果获取依据，只从原始文档和代码出发做独立判断。**

你接收审核报告后，对存疑和遗漏项做最终裁决，整合审核结果到阶段 6 报告的"七、独立审核结果"章节。

**审核完成后自动进入阶段 8，无需用户确认。**

---

### 阶段 8：代码实现

审核完成后，派发 **1 个 general-purpose sub-agent** 执行代码实现。

**Agent prompt 必须包含：**
- 阶段 6 的最终报告（含阶段 7 审核结果）
- 当前题目编号
- 项目根目录路径
- 指令：严格按照报告的实现清单逐项编码

**Agent 工作步骤：**

1. 读取报告的"六、实现清单"，按优先级顺序（P0 → P1 → ...）逐项修改代码
2. 编译验证：`cd build && cmake .. && make -j$(nproc)`
3. 运行测试验证
4. 如编译或测试失败，修复后重新验证
5. **禁止执行 git commit**

**冲突处理规则：**

- 与满分分支不一致时：默认跟随满分分支（核心目标是通过该题拿到满分）
- 审核中的存疑项：agent 根据题目要求自行判断，以通过题目为目标
- 审核中的遗漏项：先补齐遗漏的分析，再实现对应代码
- 只有在上下文和题目要求都无法决策时，才暂停并报告需要人工介入

**Agent 必须返回：**
- 修改的文件列表（路径 + 改动摘要）
- 编译结果（通过/失败 + 错误信息）
- 测试结果（通过数/失败数 + 失败的测试名）
- 是否全部通过
- 如有未通过的测试，说明原因

## 输出完成

阶段 8 完成后，此 skill 结束。代码已修改在磁盘上，编译测试通过。

**用户自行 `git commit` 并提交在线评测。**

## 安全规则

1. **满分分支只读**：通过 git worktree 隔离操作，绝不修改满分分支
2. **禁止合并分支**：绝不执行 `git merge`
3. **提交由用户手动操作**：代码实现 agent 可写代码但不做 git commit，用户自行提交
4. **题目规格优先**：满分分支的输出如果不符合题目要求，以题目要求为准

## 与其他技能的协作

- 若阶段 8 实现后测试不通过，使用 `systematic-debugging` 独立调试
- 编码完成后的提测和验收使用 `verification-before-completion`
- 代码提交由用户手动操作，或通过 `git-helper` 辅助
