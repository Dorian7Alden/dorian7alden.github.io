# 方法论二：假设驱动闭环

> **前置依赖**：此方法需要可重复的基准负载 + profiling 数据。当前测试框架尚未建立，此方法暂不可用。以下内容保留作为测试框架就绪后的操作指南。

适合：有可测量的性能数据，需要定位具体瓶颈的场景。

核心思想：优化不是"我觉得这里慢"，而是"通过测量发现 X 环节消耗 Y% 资源，推测原因是 Z，通过改动验证"的科学闭环。

## 流程

### 1. 建立基准

跑一次可重复的负载，记录吞吐、延迟、资源消耗作为基准值。确保每次改动后能用相同条件对比。

### 2. 多维剖析，画延迟瀑布图

把请求路径拆成阶段：

```
网络接收 → 解析 → 规划 → 执行 → 存储存取 → 事务提交 → 网络返回
```

对每个阶段单独计时，判断瓶颈在：
- **CPU**：计算密集、分支预测失败、缓存缺失
- **内存**：分配/拷贝/碎片
- **I/O**：随机读写频率、带宽利用率
- **争用**：锁/闩锁/原子变量等待

工具参考：perf、火焰图、blktrace、iostat、eBPF。

### 3. 提出假设

例："Hash Join 耗费 40% CPU，原因是键哈希碰撞率高且数据不连续导致 cache miss。"

假设必须指明：哪个环节、消耗占比、推测根因。

### 4. 最小可行变更，单变量验证

每次只改一个因素，严格对比改动前后的指标。失败的假设同样有价值——排除一个方向，聚焦其他。

### 5. 迭代

消除一个瓶颈后，新的热点会暴露。性能优化就是不断测量、假设、验证的循环。

## 与特征驱动法的区别

| | 特征驱动 | 假设驱动 |
|---|---|---|
| 出发点 | 代码特性 → 找浪费 | 测量数据 → 推根因 |
| 适合时机 | 代码审查、静态分析 | 有 profiling 数据后 |
| 强项 | 快速发现明显浪费 | 精准定位深层瓶颈 |

两种方法可以混合：先用特征驱动快速扫一遍明显浪费，再用假设驱动深挖 profiling 里的隐藏问题。
