# 方法一：特征驱动

核心思想：利用系统中已有的各种特性去省开销。不盲目全量分析，每次聚焦一个点。

## 第一步：锁定目标

选定一个具体的分析对象——一个模块、一个函数、一条热路径。**不分析全系统，只聚焦一个点。**

判定标准：
- 运行频次高（每条记录操作都经过）
- 有可观测特征（syscall、内存分配、锁、I/O 等可数可量）
- 调用粒度大（一次操作背后触发了多次子操作）

> 参考 `optimization-theory.md` 第一章"定义目标 / 工作负载画像"——先明确要优化的是吞吐、延迟还是并发，不同目标导向的优化路径截然不同。

## 第二步：提取特性

从 `dev-doc/system-characteristics/<模块名>/` 拉出该模块的已有特性，补充缺失的点：

- 参数的值范围、边界值
- 数据结构的大小、访问模式
- 调用频率、触发条件（热路径/冷路径）
- 资源粒度（一次 syscall 的 payload 大小、一次锁保护的代码量）
- 并发模型（谁跟谁共享、谁跟谁互斥）

格式自由，但每条特性必须包含：值/范围、性质（静态推导/动态测试）、来源（代码位置或测试记录）、优化关联（影响什么性能决策）。

**这一步的产出是一组精确的事实，不是猜测。**

## 第三步：找浪费点

用特性去比对实际行为，找"可以做但没有被省掉的开销"。

常见浪费类型：

| 类型 | 信号 | 案例 |
|------|------|------|
| 冗余 syscall | 两次调用可合并为一次 | lseek+write → pwrite |
| 冗余计算 | 同输入反复算同一结果 | 哈希值被重复计算 |
| 锁粒度过粗 | 一把锁保护了不需要串行化的代码 | 单 latch 保护所有 fd |
| 缓冲区浪费 | 分配了大量不用或少用的空间 | 数组远大于实际使用 |
| 内存屏障过剩 | 用了 seq_cst 但只需 relaxed | atomic++ 默认最强序 |
| 碰撞/退化 | 哈希分布不均导致链表遍历 | 位拼接替代哈希打散 |

> 参考 `optimization-theory.md` 第三章"内核优化全景维度"——从存储引擎、查询处理、并发事务、内存数据流、并行分布式五个层面系统地扫描可能的优化方向，作为启发式清单。

## 第四步：提出方案

方案必须有：
- **理论依据**：参考已知的最佳实践（POSIX 规范、并发理论、缓存友好的数据结构、业界惯例等）
- **改动边界**：只改什么、不动什么
- **预估收益**：省了多少 syscall/时钟周期/锁等待/内存

对于调参类优化，注明"最优值需实测确定"。

## 第五步：安全验证

**必须**启动 subAgent（`isolation: worktree`），在独立分支上完成：
- 理论分析：改动是否会引入新 bug、数据竞争、逻辑错误
- 编译测试：`cd build && cmake .. && make -j$(nproc) && make unit_test && ./bin/unit_test`
- 汇报结果：编译通过否、测试全绿否、风险分析结论

**只有 subAgent 确认安全后，才能进入下一步。**

## 第六步：实测对比

改动前后跑相同负载，记录定量数据。对于调参类优化这是核心环节——最优值只有实测才能确定。

## 第七步：沉淀文档

改动完成后必须同步更新：
1. **`dev-doc/system-characteristics/`**：如果发现新特性或静态特性变为动态特性
2. **`dev-doc/code-explain/`**：如果改动涉及值得讲解的技术点
3. **`dev-doc/performance-improve/`**：创建优化记录，含前后对比、收益分析、安全性论证

> 当面临多个优化方向互斥时，参考 `optimization-theory.md` 第四章"权衡：核心决策罗盘"——读 vs 写、延迟 vs 吞吐、空间 vs 时间，每一项设计都是在权衡曲线上选择位置。
