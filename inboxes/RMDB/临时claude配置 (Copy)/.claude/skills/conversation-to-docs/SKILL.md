# 对话整理成文档 + 文档库维护

两种工作模式，根据用户意图自动选择：

- **创建模式**：从当前会话提取讲解内容，产出新文档或追加到已有文档
- **维护模式**：审计已有文档，发现冗余、缺口、过时内容，优化结构

## 核心原则

- **只整理与项目讲解、答疑、知识传递有关的对话**。杂七杂八的聊天、闲聊、纯操作指令不纳入
- **拆分多个文档**，按主题分类。一个文档聚焦一个主题，不要把所有内容塞进一个文件
- **渐进式**，从概述到细节，从高层到底层
- **像写教程**，补充前置知识、展开缩略语、解释术语，让不了解项目的读者也能看懂
- **中文文档**，面向中文阅读者

## 文档编号规范

数字编号（00-, 01-, 02-...）只用于有阅读顺序的渐进式教程文档。通用参考文档（术语表、附录）用描述性文件名（如 `glossary.md`），放在数字编号文档的后面，不插在教程编号中间。

# 创建模式

从当前会话中提取讲解内容，产出文档。

## 步骤 1: 回顾会话，提取话题

完整回顾当前会话的所有对话，识别出所有"讲解/答疑"性质的话题。跳过：
- 纯操作指令（"运行这个命令"、"帮我改这行代码"）
- 与项目理解无关的闲聊
- 重复确认的内容

输出一个话题清单，展示给用户确认。

## 步骤 2: 规划文档结构

按主题将话题分组，规划成多个文档。原则：
- 一个文档一个主题
- 有分类意识——方便日后快速定位知识点
- 遵守文档编号规范
- 输出到 `dev-doc/` 目录（如果用户不指定其他位置）
- **确定主体源文件**：文档归入 `code-explain/<主体源文件名不含扩展名>/`。主体源文件是用户提问所针对的类/函数的定义所在文件，不是问题中引用的类型/常量定义文件。例如问 BufferPoolManager 构造函数 → 归入 `buffer_pool_manager/`，即使问题涉及 `Page` 和 `PAGE_SIZE` 也不归入 `page/` 或 `config/`。

展示文档规划给用户确认。

## 步骤 3: 逐个编写文档

一个一个写，每写完一个再写下一个。

**内容规范**：
- 开头说明"本文档讲什么"，让读者知道该不该读
- 大纲清晰，标题层级分明（`##` 主标题，`###` 子标题）
- 像写教材一样——有前置知识铺垫，有术语解释，有例子
- 遇到缩略语必须展开全称（如 `fd` = file descriptor，文件描述符）
- 遇到变量命名要解释含义
- 结尾有总结或指向后续文档的链接

**格式规范**：
- 用 mermaid 画流程图、类图、层次图
- mermaid 不适合的场景（紧凑的内存布局、字节排布），用纯文本块 + 文字化图
- 代码片段用 ```cpp 或 ```text
- 不要滥用 emoji

每写完一个文档后，简要告知用户写了什么，再继续写下一个。

## 步骤 4: 交叉检查遗漏

所有文档写完后，对照步骤 1 的话题清单逐一核对：
- 每个话题是否都有对应的文档覆盖？
- 如果某个话题在多个文档中都有涉及，是否需要在某处做集中讲解？
- 列出遗漏话题，询问用户是否需要补充。

## 步骤 5: 迭代补充

如果用户指出遗漏或需要修改的地方，补充到对应文档中。补充完毕后更新受影响的文档。如果有新文档，更新 `00-overview.md` 中的文档索引。

# 维护模式

当用户要求"维护文档""检查文档""审计文档""整理文档""看看文档有没有问题"时启动。目标是让文档库保持健康：内容不过时、结构合理、对新人友好。

## 步骤 1: 通读现有文档

先读 `dev-doc/` 下所有 `.md` 文件，建立全局认知：每个文档的主题、长度、定位。

## 步骤 2: 五维审计

从以下五个维度逐项检查，找出问题。

**A. 覆盖缺口** — 对比项目架构（CLAUDE.md 中的关键模块列表、src/ 目录结构）和文档内容，找出没被覆盖的重要模块/概念。标注每个缺口的重要程度（核心/重要/可选）。

**B. 内容冗余** — 检查多个文档之间是否大段重复讲解同一内容。少量交叉引用正常，但大段重复需要合并或去重。报告格式：`01-xxx.md 的 "XXX 节" 和 03-yyy.md 的 "YYY 节" 都在讲 ZZZ，建议保留一处，另一处改为链接引用`。

**C. 文档过时** — 对比文档内容和当前代码。检查引用的文件路径是否还存在、描述的数据结构/函数签名是否和代码一致、提到的 TODO/未来规划是否已经实现或废弃。

**D. 结构合理性** — 检查：有没有单文档过长（>500 行）需要拆分的？有没有两篇内容高度相关应合并的？编号顺序是否符合阅读依赖？非教程文档是否被错误地编入了数字编号？`00-overview.md` 的索引是否包含了所有文档？

**E. 新人友好度** — 以新人视角审视：每份文档开头是否有明确的"本文档讲什么"？缩略语首次出现时是否展开了全称？核心概念是否有通俗解释？文档间的引用链接是否有效？

## 步骤 3: 输出审计报告

按以下格式逐条列出发现和建议，让用户逐条确认：

```
文档审计报告
============

A. 覆盖缺口
  - [核心] 事务模块完全没有文档覆盖
  - [重要] BufferPool 淘汰策略缺少深入讲解
  - [可选] plan_query() 方法未展开

B. 内容冗余
  - ...

C. 文档过时
  - ...

D. 结构合理性
  - ...

E. 新人友好度
  - ...

建议优先级
  1. ...（最紧急）
  2. ...
```

## 步骤 4: 逐条处理

用户确认后，逐条执行修改。修改完后更新报告状态。

## 维护的边界

- **只针对 `dev-doc/` 目录下的文档**，不改项目代码
- **合并文档时保留所有有价值的内容**，不能丢信息
- **重命名文件时更新所有交叉引用**
- **每次维护结束后更新 `00-overview.md` 的索引**
