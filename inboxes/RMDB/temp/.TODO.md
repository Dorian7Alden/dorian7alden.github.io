# BenchBase 性能测试框架完整使用指南（面向自定义数据库/数据库系统能力大赛）
本文档面向无性能测试经验、基于RMDB框架开发自定义数据库的参赛选手，从框架原理、环境搭建、自定义数据库适配、完整测试流程到结果分析全流程讲解，帮助你从零开始完成数据库性能测试。

---

## 一、框架概述与核心价值
### 1.1 什么是 BenchBase
BenchBase 前身是学术界广泛使用的 OLTP-Bench，是卡内基梅隆大学（CMU）维护的**多数据库通用SQL基准测试框架**，完全基于JDBC协议与数据库交互，支持几乎所有兼容JDBC的关系型数据库。

它的核心定位是：提供标准化的业务负载模拟，统一统计吞吐量、延迟等核心性能指标，让不同数据库、不同优化版本的性能可以横向对比。

### 1.2 对你的数据库大赛项目的作用
1. **量化性能表现**：用行业通用指标（TPS、P99延迟）客观衡量你的数据库性能，避免主观判断。
2. **验证功能正确性**：通过标准事务负载验证事务ACID、并发控制、索引等核心模块的正确性。
3. **定位性能瓶颈**：通过不同并发、不同负载的测试，定位你的数据库是CPU瓶颈、IO瓶颈还是锁冲突瓶颈。
4. **对比优化效果**：每次代码优化前后跑相同测试，量化优化带来的性能提升。

### 1.3 核心特性
- 内置近20种业界标准基准测试，覆盖OLTP、OLAP、混合负载等场景。
- 支持多线程并发压测，可自定义并发数、测试时长、预热时间、事务比例。
- 自动完成「建表→加载数据→压测」全流程，无需手动准备数据。
- 自动输出详细的性能统计结果，支持CSV/JSON格式导出。
- 完全开源可扩展，支持适配自定义数据库。

---

## 二、前置准备与核心概念扫盲
### 2.1 系统与软件环境
- **JDK版本**：必须使用 Java 17 或 Java 21（框架官方指定版本，低版本会编译失败）。
- **Git**：用于克隆项目代码。
- **Maven**：项目自带 `mvnw`（Maven包装器），无需单独安装Maven。
- 操作系统：Windows、Linux、macOS均可，推荐Linux/macOS，命令更顺畅。

### 2.2 你的自定义数据库必须满足的前提（重中之重）
BenchBase 完全基于 JDBC 协议和数据库通信，因此你的RMDB数据库必须满足以下条件才能接入：
1. **具备可用的JDBC驱动**：实现了JDBC核心接口（`java.sql.Driver`、`Connection`、`Statement`、`PreparedStatement`、`ResultSet`）。
2. **支持标准SQL语法**：至少支持基础DDL（建表、建索引）、DML（增删改查）、事务提交/回滚。
3. **可通过URL连接**：有标准的JDBC URL格式（如 `jdbc:rmdb://localhost:端口/数据库名`），支持用户名密码认证。

> 提示：如果你的RMDB框架已经内置了JDBC驱动，可直接使用；如果还没有实现JDBC层，需要先完成基础JDBC接口开发，再接入BenchBase。

### 2.3 新手必看：核心性能概念
| 概念 | 说明 |
|------|------|
| **TPS（每秒事务数）** | 数据库每秒能完成的事务总数，是衡量性能的核心指标，数值越高性能越好。 |
| **延迟（Latency）** | 单个事务从发起到完成的耗时，常用分位值表示：<br>- P50：50%的事务延迟低于该值（中位数）<br>- P95：95%的事务延迟低于该值<br>- P99：99%的事务延迟低于该值<br>分位值比平均值更能反映真实用户体验。 |
| **并发数（Terminals）** | 同时向数据库发送请求的线程数，模拟多个用户同时访问。 |
| **预热时间（Warmup）** | 正式统计前先跑一段时间，让数据库缓存、JVM编译生效，避免冷启动干扰结果。 |
| **基准测试（Benchmark）** | 一套标准化的业务场景和事务逻辑，比如TPC-C模拟电商订单仓储业务。 |

## 三、快速上手：先跑通官方示例（熟悉流程）
建议你先用内置支持的SQLite数据库跑通一次完整流程，熟悉命令和输出后，再适配自己的RMDB数据库。SQLite是文件型数据库，无需安装服务端，零成本上手。

### 3.1 第一步：克隆项目
打开终端，执行以下命令：
```bash
# 克隆项目（--depth 1 只拉取最新代码，速度更快）
git clone --depth 1 https://github.com/cmu-db/benchbase.git
cd benchbase
```

### 3.2 第二步：构建项目
执行Maven打包命令，激活SQLite对应的profile：
```bash
# Linux/macOS
./mvnw clean package -P sqlite

# Windows
mvnw.cmd clean package -P sqlite
```
- `clean`：清理旧的构建产物
- `package`：编译并打包成可执行的压缩包
- `-P sqlite`：激活SQLite数据库的配置，自动引入SQLite的JDBC驱动

构建成功后，产物会生成在 `target` 目录下，包含 `benchbase-sqlite.tgz` 和 `benchbase-sqlite.zip`。

### 3.3 第三步：执行第一次性能测试
我们用最简单的 `noop`（空操作）基准测试来验证流程，它几乎不执行复杂SQL，适合快速跑通。
```bash
# 进入target目录，解压产物
cd target
tar xvzf benchbase-sqlite.tgz
cd benchbase-sqlite

# 执行测试
java -jar benchbase.jar -b noop -c config/sqlite/sample_noop_config.xml --create=true --load=true --execute=true
```

参数解释：
- `-b noop`：指定基准测试类型为noop
- `-c 配置文件路径`：指定对应数据库的测试配置文件
- `--create=true`：自动执行建表操作
- `--load=true`：自动加载测试数据
- `--execute=true`：正式执行压测并统计结果

### 3.4 查看测试结果
执行完成后，控制台会输出性能汇总表，包含：
- 总吞吐量（TPS）
- 每个事务类型的执行次数、平均延迟、P50/P95/P99延迟
- 测试总时长、并发数等信息

同时当前目录会生成 `results` 文件夹，里面有CSV格式的详细结果文件，可用于后续分析。

## 四、核心运行机制详解
### 4.1 三大执行阶段
BenchBase 每次测试分为三个独立阶段，可通过参数单独控制开关：
1. **Create（建表阶段）**
   读取基准测试对应的DDL脚本，在目标数据库中创建表、索引、约束等对象。
   适合场景：第一次测试、修改表结构后。

2. **Load（数据加载阶段）**
   根据配置的数据规模，自动生成模拟数据并批量插入数据库。
   注意：数据加载只需执行一次，后续重复压测无需重复加载，节省时间。

3. **Execute（压测执行阶段）**
   启动指定数量的并发线程，按照配置的事务比例循环执行事务，同时实时统计吞吐量、延迟等指标。预热时间内不统计结果，正式运行时间内的结果才会纳入统计。

### 4.2 配置文件核心结构
所有测试参数都在XML配置文件中定义，路径为 `config/数据库名/xxx_config.xml`，核心模块如下：
```xml
<?xml version="1.0"?>
<parameters>
  <!-- 1. 数据库连接配置 -->
  <connection>
    <driver>org.sqlite.JDBC</driver>          <!-- JDBC驱动类全路径 -->
    <url>jdbc:sqlite:benchbase_test.db</url>  <!-- JDBC连接URL -->
    <username></username>                     <!-- 用户名 -->
    <password></password>                     <!-- 密码 -->
  </connection>

  <!-- 2. 并发与时长配置 -->
  <terminals>4</terminals>                <!-- 并发线程数 -->
  <warmup>10</warmup>                     <!-- 预热时间（秒） -->
  <runtime>30</runtime>                   <!-- 正式测试时间（秒） -->

  <!-- 3. 数据规模配置（不同基准测试参数不同） -->
  <scalefactor>1</scalefactor>            <!-- 数据规模系数 -->

  <!-- 4. 事务比例配置 -->
  <workload>
    <transaction name="NoOp">
      <weight>100</weight>                <!-- 该事务占比，总和为100 -->
    </transaction>
  </workload>
</parameters>
```

## 五、重点：适配你的自定义 RMDB 数据库
这是整个流程最核心的部分。官方默认只支持PostgreSQL、MySQL等主流数据库，自定义数据库需要手动完成适配。

### 5.1 适配整体流程
```
引入JDBC驱动 → 添加Maven Profile → 创建配置目录 → 编写测试配置 → 适配SQL方言 → 编译验证 → 跑通最简测试
```

### 5.2 步骤1：引入你的JDBC驱动依赖
你的JDBC驱动通常是本地jar包，需要先让Maven能识别到它，有两种方式：

#### 方式A：安装到本地Maven仓库（推荐）
```bash
mvn install:install-file \
  -Dfile=/path/to/your/rmdb-jdbc.jar \
  -DgroupId=com.yourteam \
  -DartifactId=rmdb-jdbc \
  -Dversion=1.0.0 \
  -Dpackaging=jar
```

#### 方式B：直接在pom中引入本地jar
将驱动jar放到项目 `lib` 目录下，后续配置依赖时指定路径。

### 5.3 步骤2：添加自定义数据库的Maven Profile
打开项目根目录的 `pom.xml`，参考其他数据库的profile，添加你的RMDB配置：
```xml
<profile>
  <id>rmdb</id>  <!-- 自定义profile名称，构建时用 -P rmdb 激活 -->
  <dependencies>
    <!-- 你的JDBC驱动依赖 -->
    <dependency>
      <groupId>com.yourteam</groupId>
      <artifactId>rmdb-jdbc</artifactId>
      <version>1.0.0</version>
    </dependency>
  </dependencies>
</profile>
```

### 5.4 步骤3：创建数据库专属配置目录
在 `config` 目录下新建 `rmdb` 文件夹，复制 `config/sqlite` 或 `config/postgres` 里的配置文件到该目录，后续修改使用。

### 5.5 步骤4：编写基准测试配置文件
以最简的 `noop` 测试为例，新建 `config/rmdb/sample_noop_config.xml`，修改连接信息：
```xml
<?xml version="1.0"?>
<parameters>
  <connection>
    <!-- 替换为你的JDBC驱动类全类名 -->
    <driver>com.yourteam.rmdb.jdbc.Driver</driver>
    <!-- 替换为你的数据库连接URL、端口、数据库名 -->
    <url>jdbc:rmdb://localhost:8888/testdb</url>
    <!-- 替换为你的数据库用户名密码 -->
    <username>admin</username>
    <password>123456</password>
  </connection>

  <terminals>2</terminals>    <!-- 新手先设小并发，跑通为主 -->
  <warmup>5</warmup>          <!-- 预热5秒 -->
  <runtime>20</runtime>       <!-- 正式测试20秒 -->

  <workload>
    <transaction name="NoOp">
      <weight>100</weight>
    </transaction>
  </workload>
</parameters>
```

### 5.6 步骤5：SQL方言与语法适配
这是适配中最容易踩坑的环节。不同数据库的SQL语法、数据类型、内置函数都有差异。

#### 适配原则
1. **从最简单的基准测试开始**：优先适配 `noop` → `smallbank` → `tpcc`，不要一上来就搞复杂负载。
2. **修改对应DDL脚本**：每个基准测试的SQL脚本存放在 `src/main/resources/benchmarks/<测试名>/` 目录下。
3. **逐句验证**：把DDL语句放到你的数据库里手动执行，排查语法错误。

#### 常见适配点
- **数据类型**：比如 `BIGSERIAL`（PG自增）、`AUTO_INCREMENT`（MySQL自增）要替换成你的数据库支持的自增写法；不支持的类型替换为等价类型。
- **约束语法**：主键、外键、唯一约束的语法差异。
- **内置函数**：比如 `NOW()`、`CURRENT_TIMESTAMP` 等时间函数，替换为你的数据库支持的函数。
- **分页语法**：比如 `LIMIT` 是否支持，语法是否一致。

> 提示：如果你的数据库语法和MySQL/PostgreSQL接近，可以直接对应参考它们的方言文件，修改量会小很多。

### 5.7 步骤6：编译并验证适配
1. 构建RMDB版本的BenchBase：
```bash
./mvnw clean package -P rmdb
```
2. 解压产物，执行最简测试：
```bash
cd target
tar xvzf benchbase-rmdb.tgz
cd benchbase-rmdb

# 先只测试建表，验证DDL是否正确
java -jar benchbase.jar -b noop -c config/rmdb/sample_noop_config.xml --create=true --load=false --execute=false
```
3. 建表成功后，逐步开启load和execute：
```bash
# 测试数据加载
java -jar benchbase.jar -b noop -c config/rmdb/sample_noop_config.xml --create=false --load=true --execute=false

# 完整执行压测
java -jar benchbase.jar -b noop -c config/rmdb/sample_noop_config.xml --create=false --load=false --execute=true
```

如果完整执行成功，控制台输出了TPS和延迟数据，恭喜你，你的数据库已经成功接入BenchBase了！

## 六、完整性能测试执行流程（从0到1）
适配完成后，就可以按照标准流程进行正式的性能测试了。

### 6.1 阶段1：规划测试场景与参数
正式测试前一定要先规划，避免盲目跑数。建议先确定：
1. **测试目标**：比如「测试TPC-C负载下的并发扩展性」「验证索引优化后的性能提升」。
2. **选择基准测试**：根据你的数据库完成度选择（选型建议见第八章）。
3. **固定测试参数**：
   - 数据规模：比如TPC-C设为1个仓库，全程不变。
   - 预热时间：建议30~60秒，排除冷启动影响。
   - 正式测试时长：建议120~300秒（2~5分钟），结果更稳定。
   - 并发数梯度：比如 1、2、4、8、16，逐步增加，测试扩展性。
4. **重复次数**：每组参数至少跑3次，取平均值，排除偶然波动。

### 6.2 阶段2：初始化数据库
1. 启动你的RMDB数据库，创建专用的测试数据库。
2. 执行建表操作，确认表结构创建成功：
```bash
java -jar benchbase.jar -b tpcc -c config/rmdb/sample_tpcc_config.xml --create=true --load=false --execute=false
```
3. 手动登录数据库，检查表、索引是否创建正确。

### 6.3 阶段3：加载测试数据
```bash
java -jar benchbase.jar -b tpcc -c config/rmdb/sample_tpcc_config.xml --create=false --load=true --execute=false
```
- 加载过程中观察控制台输出，确认数据量符合预期，无报错。
- 数据加载只需要做一次，后续压测复用这批数据即可。
- 调试阶段建议用最小数据量，提高效率；正式测试再用标准规模。

### 6.4 阶段4：执行压测
```bash
java -jar benchbase.jar -b tpcc -c config/rmdb/sample_tpcc_config.xml --create=false --load=false --execute=true
```
- 测试过程中不要操作数据库，也不要关闭终端。
- 进阶操作：可以同时开启系统监控（CPU、内存、磁盘IO），辅助定位瓶颈。

### 6.5 阶段5：保存与整理结果
1. 每次测试完成后，新建文件夹保存结果，命名规则建议：`测试名_并发数_版本号_日期`。
2. 保存内容：控制台输出截图、results目录下的所有结果文件、本次测试的配置文件。
3. 记录备注：比如本次测试的特殊配置、优化点，方便后续对比。

## 七、测试结果解读与性能分析方法
### 7.1 核心指标优先级
**正确性 > 吞吐量 > 延迟稳定性 > 平均延迟**
1. **事务成功率**：必须100%。只要有事务失败，先解决功能bug，再谈性能。
2. **吞吐量（TPS）**：核心性能指标，直接反映数据库的处理能力。
3. **P99延迟**：反映极端情况下的性能表现，比平均延迟更重要。
4. **吞吐量稳定性**：测试全程TPS是否平稳，大幅波动说明有性能抖动。

### 7.2 结果文件解析
BenchBase 会输出两类核心结果文件：
1. **汇总CSV**：包含每个事务类型的执行次数、平均延迟、各分位延迟、TPS等汇总数据，可直接用Excel打开查看。
2. **间隔统计CSV**：按时间窗口（默认每秒）统计吞吐量和延迟，可用来绘制性能随时间变化的曲线，观察稳定性。

### 7.3 性能分析通用思路
#### 第一步：做基线测试
先跑单并发（terminals=1）的测试，得到单线程下的TPS和延迟，作为性能基线。这个指标反映了单事务的纯执行效率，和你的执行器、存储引擎的代码效率直接相关。

#### 第二步：做并发扩展性测试
逐步增加并发数，绘制「并发数-TPS」曲线，观察：
- 线性增长阶段：并发数增加，TPS近似线性增长，说明数据库扩展性好。
- 拐点：当并发数增加到某个值，TPS增长放缓甚至下降，说明到达了数据库的性能瓶颈。
- 下降阶段：并发继续增加，TPS不升反降，通常是锁冲突、上下文切换开销过大导致的。

#### 第三步：定位瓶颈方向
| 现象 | 可能的瓶颈 |
|------|------------|
| CPU占用拉满，IO很低 | 计算瓶颈：SQL解析慢、执行器效率低、事务处理逻辑冗余 |
| 磁盘IO很高，CPU空闲 | 存储瓶颈：刷盘太频繁、缓存命中率低、索引没命中导致全表扫描 |
| 并发上去TPS不涨，CPU和IO都不高 | 锁冲突瓶颈：事务锁粒度太大、死锁/等待多、并发控制算法效率低 |
| 延迟波动大，忽高忽低 | 稳定性问题：GC、周期性刷盘、锁竞争不均匀 |

### 7.4 数据库大赛常用对比维度
1. **优化前后对比**：同一参数下，对比优化代码前后的TPS提升比例、延迟下降比例。
2. **不同并发下的性能曲线**：展示数据库的并发扩展能力。
3. **不同读写比例对比**：调整事务比例，测试读多写少、写多读少场景的表现。
4. **不同数据规模对比**：测试数据量增大后性能的衰减情况。

## 八、适合数据库大赛的基准测试选型
根据数据库完成度，循序渐进选择：

### 8.1 入门级：验证基础功能
| 测试名 | 适用场景 | 特点 |
|--------|----------|------|
| **NoOp** | 适配验证、框架开销测试 | 几乎不执行实际SQL，只测连接和基础通信，最快跑通 |
| **SIBench** | 二级索引性能测试 | 简单的插入+索引查询，验证索引功能和基础性能 |
| **SmallBank** | 事务功能验证 | 简单银行模型，3张表、3种事务，逻辑简单，适合验证事务ACID |

### 8.2 进阶级：测事务与并发（核心比赛指标）
| 测试名 | 适用场景 | 特点 |
|--------|----------|------|
| **TPC-C** | 核心OLTP性能测试 | 行业最经典的事务基准，模拟订单仓储业务，5种事务，读写混合，是大赛最有说服力的测试项 |
| **TATP** | 读密集型性能测试 | 模拟电信订阅业务，读多写少，短事务，测高并发查询能力 |
| **YCSB** | 灵活CRUD测试 | KV风格负载，可自定义读写比例，适合测基础增删改查性能 |

### 8.3 高阶：复杂场景测试
| 测试名 | 适用场景 | 特点 |
|--------|----------|------|
| **CH-benCHmark** | 混合负载测试 | 同时跑TPC-C事务+TPC-H查询，测OLTP+OLAP混合场景 |
| **TPC-H** | OLAP分析性能 | 复杂聚合查询、多表关联，测查询优化器能力 |

> 参赛建议：优先搞定 TPC-C，它是数据库大赛的「事实标准」，最能体现数据库的综合实力。

## 九、常见问题与避坑指南
### 9.1 构建与依赖问题
- `mvnw` 无执行权限：执行 `chmod +x mvnw`。
- Maven下载依赖慢：在 `~/.m2/settings.xml` 中配置阿里云Maven镜像。
- 驱动类找不到：检查profile是否激活、依赖的groupId/artifactId/version是否匹配。

### 9.2 数据库连接问题
- `ClassNotFoundException`：驱动类名写错，或者JDBC驱动没有正确引入依赖。
- `Connection refused`：数据库未启动、端口错误、URL地址错误。
- 认证失败：用户名密码错误，或者你的数据库未开启密码认证。

### 9.3 SQL语法报错
- 建表报错：逐句执行DDL，逐个修改不兼容的语法，优先保证能建表，再考虑性能。
- 函数不支持：替换为你的数据库支持的函数，或者在SQL中去掉非必要函数。
- 事务报错：确认你的数据库支持 `commit`/`rollback`，且默认关闭自动提交。

### 9.4 数据加载问题
- 加载特别慢：调试阶段用最小数据量；检查是否支持批量插入，逐条插入会非常慢。
- 内存溢出：执行时加大JVM堆内存，比如 `java -Xmx4g -jar benchbase.jar ...`。
- 主键冲突：检查数据生成逻辑是否重复，或者你的数据库主键约束是否正确。

### 9.5 结果异常问题
- TPS为0：事务执行卡住了，大概率是锁等待或死锁，检查你的并发控制逻辑。
- 延迟异常高：检查是否每次事务都强制刷盘、是否全表扫描没命中索引。
- 结果波动大：延长预热时间和测试时长，增加测试次数取平均。

## 十、给新手的进阶建议
1. **先保证正确，再追求性能**：功能不对，性能再高也没有意义。每次测试先确认事务100%成功、数据一致。
2. **控制变量**：对比测试时，只改变一个变量（比如只改并发数，或者只改一个优化点），否则无法确定性能变化的原因。
3. **做好测试记录**：建立测试记录表，每次测试记录版本、参数、指标、备注，积累优化轨迹。
4. **小步快跑**：调试阶段用小数据量、短时长，快速验证；正式出结果再用标准参数跑长时间。
5. **善用对比**：可以先拿SQLite或MySQL跑同样的测试，作为参考基准，看看你的数据库和主流数据库的差距在哪里。

如果你需要针对某个具体基准测试（比如TPC-C）的详细适配步骤，或者需要帮你解读测试结果、分析瓶颈方向，我可以进一步展开讲解。
