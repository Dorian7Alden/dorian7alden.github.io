# 多表连接执行问题总结

## 背景

本次问题出现在多表查询执行阶段，主要涉及以下 SQL：

```sql
select * from t, d;
select t.id, t_name, d_name from t, d where t.id = d.id;
select t.id, t_name, d_name from t join d where t.id = d.id;
```

其中 `select * from t, d;` 初始会在顶层投影算子中报列找不到，后续修复后笛卡尔积可以输出，但带连接条件的查询仍返回 0 条记录。

## 已修复问题

### 1. JoinExecutor 没有向上暴露输出列元数据

顶层 `ProjectionExecutor` 会通过子执行器的 `cols()` 查找需要投影的列：

```cpp
auto &prev_cols = prev_->cols();
auto pos = get_col(prev_cols, sel_col);
```

多表查询时，投影算子的子节点是 `NestedLoopJoinExecutor`。如果 `NestedLoopJoinExecutor` 没有重写 `cols()` 和 `tupleLen()`，就会调用 `AbstractExecutor` 的默认实现，导致顶层投影拿不到 join 后拼接记录的列元数据。

解决方式是在 `NestedLoopJoinExecutor` 中返回 join 后的列集合和记录长度：

```cpp
const std::vector<ColMeta> &cols() const override {
    return cols_;
}

size_t tupleLen() const override {
    return len_;
}
```

这样顶层投影可以正确找到 `t.id`、`t.t_name`、`d.d_name`、`d.id` 等列。

### 2. 连接条件判断中右表记录指针悬空

原代码在 `check_conditions()` 中直接写：

```cpp
const char* right_data = right_->Next()->data;
```

`right_->Next()` 返回的是临时 `std::unique_ptr<RmRecord>`，这一行执行结束后临时对象析构，`right_data` 指向已经释放的内存。后续比较 `t.id = d.id` 时使用悬空指针，结果不可预期，实际表现为连接条件查询返回 0 条记录。

解决方式是延长右表记录对象生命周期：

```cpp
auto right_record = right_->Next();
if (!right_record) {
    return false;
}
const char* right_data = right_record->data;
```

这样在条件比较结束前，`right_data` 始终指向有效记录数据。

## 当前还没充分考虑的问题

### 1. Join 输出顺序不应作为正确性判断依据

当前 `select * from t, d;` 输出顺序和示例期望顺序不同。例如实际可能是：

```text
1 aaa 12345 1
1 aaa 23456 2
2 baa 12345 1
2 baa 23456 2
3 bba 12345 1
3 bba 23456 2
```

示例期望可能把 `d` 表中的两条记录按不同顺序输出。

这个差异本身不是 SQL 执行错误，因为没有 `order by` 的查询不保证输出顺序。测试时不应依赖无序查询的行顺序，只应比较结果集合是否一致。

如果必须得到固定顺序，应显式加排序，例如：

```sql
select * from t, d order by t.id, d.id;
```

或者在测试框架中对结果按列排序后再比较。

### 2. `NestedLoopJoinExecutor::Next()` 和 `check_conditions()` 都会读取右表当前记录

当前执行逻辑中：

- `advance_to_next_match()` 调用 `check_conditions()` 判断当前左右记录是否匹配；
- `Next()` 再次调用 `right_->Next()` 生成输出记录。

如果底层执行器的 `Next()` 是纯读取当前记录，这种写法可以工作；但如果未来某些执行器把 `Next()` 实现成“读取并推进”，这里就会出现状态错乱。

更稳妥的做法是让 `NestedLoopJoinExecutor` 保存当前右表记录，例如增加：

```cpp
std::unique_ptr<RmRecord> right_record_;
```

在 `advance_to_next_match()` 中找到匹配时缓存右表记录，`Next()` 直接使用缓存生成 join 结果，避免重复读取右表当前记录。

### 3. Join 条件中字符串比较长度只使用左列长度

当前字符串比较使用：

```cpp
int cmp_len = (lhs_pos->type == TYPE_STRING) ? lhs_str_len : 0;
```

这默认左右字符串列长度兼容。如果左右列都是字符串但长度不同，`strncmp` 只按左列长度比较，可能导致边界行为不符合预期。

建议在语义分析阶段继续保证比较双方类型兼容，并在执行阶段对字符串比较明确使用双方共同规则，例如：

- 相同类型但不同长度时按最大长度比较；
- 或按数据库定义的 char 定长语义处理，补齐后比较；
- 或在语义分析阶段拒绝长度不一致的字符串列比较。

### 4. `get_col()` 对重复列名依赖表名区分

多表中可能存在同名列，例如 `t.id` 和 `d.id`。当前 `get_col()` 使用：

```cpp
col.tab_name == target.tab_name && col.name == target.col_name
```

这是正确方向，但要求所有执行器向上传递的 `ColMeta.tab_name` 必须完整保留。如果后续新增投影、排序、聚合或表达式执行器时丢失 `tab_name`，多表同名列仍会再次出现找不到列或列匹配错误。

建议约定所有执行器的输出 `ColMeta` 都必须保留可用于上层解析的来源表名和列名；如果是表达式列或聚合列，则需要定义新的命名规则。

### 5. `select *` 展开后会生成重复显示列名

`select * from t, d;` 展开后实际列为：

```text
t.id, t.t_name, d.d_name, d.id
```

但输出表头只显示 `id, t_name, d_name, id`。这和很多数据库行为一致，但在测试或调试时容易混淆。

如果需要更清晰的调试输出，可以在多表查询或列名冲突时显示完整列名：

```text
t.id, t.t_name, d.d_name, d.id
```

但这会改变现有输出格式，需要确认是否符合测试要求。

### 6. 当前 IndexScanExecutor 仍是空实现

`IndexScanExecutor::beginTuple()`、`nextTuple()`、`Next()` 当前还没有真正实现。如果某个查询计划选择了 `T_IndexScan`，执行阶段会返回空或异常结果。

如果当前阶段不要求索引扫描，可以临时确保优化器不会选择未完成的 IndexScan；如果要支持索引查询，则需要完整实现索引扫描迭代、条件过滤和 `cols()` / `tupleLen()`。

## 建议后续验证用例

### 笛卡尔积

```sql
select * from t, d;
```

期望记录数为 6。无 `order by` 时不检查行顺序。

### 等值连接

```sql
select t.id, t_name, d_name from t, d where t.id = d.id;
```

期望结果集合为：

```text
1 aaa 12345
2 baa 23456
```

### 显式 join

```sql
select t.id, t_name, d_name from t join d where t.id = d.id;
```

期望结果集合同上。

### 非等值连接

```sql
select t.id, d.id from t, d where t.id > d.id;
```

用于验证 `OP_GT` 等比较操作是否正确。

### 同名列投影

```sql
select t.id, d.id from t, d where t.id = d.id;
```

用于验证多表同名列是否能通过表名正确区分。

## 总结

本次问题的核心不是 `ProjectionExecutor::get_col()` 本身，而是下层 join 执行器没有正确提供输出元数据，以及条件判断中使用了已经释放的右表记录指针。

当前修复后应重点验证：

1. 多表 `select *` 不再报列找不到；
2. 条件连接能返回匹配记录；
3. 无 `order by` 的输出顺序不作为错误判断依据；
4. 后续如果实现或启用 IndexScan，需要补齐执行器接口和迭代逻辑。
