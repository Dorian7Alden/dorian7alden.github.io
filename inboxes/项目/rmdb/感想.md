**页面淘汰算法有很多种**

| 算法  | 核心思想        | DBMS 典型场景         | 优点               | 缺点         |
| ----- | --------------- | --------------------- | ------------------ | ------------ |
| LRU   | 淘汰最近最少用  | 通用型负载（OLTP）    | 简单，命中率高     | 害怕顺序扫描 |
| Clock | LRU的近似开销小 | 最常用的折衷方案      | 性能/开销平衡好    | 不是精确LRU  |
| 2Q    | 冷热分离        | 混合负载（OLTP+OLAP） | 抗污染能力强       | 实现稍复杂   |
| MRU   | 淘汰最近最常用  | 专用于重复顺序扫描    | 在特定场景最优     | 通用场景很差 |
| ARC   | 自适应LRU+LFU   | 高级存储系统          | 适应性极强命中率高 | 极其复杂     |





RMDB 有感

- **职责分配**

每一层管理的东西都非常纯粹，负责的内容板块。

底层的数据操作层，storage layer 跟 record layer 就只是纯粹的对数据进行操作，不涉及逻辑管理之类的。数据的一致性是交给上层的事务层进行管理的。数据操作跟逻辑处理是在不同层完成的，不会交叉，职责分明，边界清晰。

底层就好像一些工具类，暴露接口给上层用，上层通过逻辑把这些接口好好利，管理。包括锁的构造，在哪个地方构造，不是每个函数都要有锁，只在入口出有锁，避免死锁。

- **生命周期**

生命周期的管理很重要。谁来管理生命周期，有严格的管理者。



C++ 中，有一个比较有意思的操作，就是传指针，最终不需要返回值，不需要 return ，只要把指针的值修改了，就可以理解为进行了一次 return。其他编程语言的思路，一般都是通过函数方法，return 一个东西，然后再通过赋值操作等，把结果赋值替换上去。前者性能更好。

因此，很多 C++ 的函数方法，返回都是 Bool 类型的，是否执行成功，入参都是指针，直接改值，不需要返回数据结果，只需要返回执行状态即可。



函数边界的非常明确。谁调用谁...入参什么时候确定







数据库事务边界控制

事务只针对于数据库，但有些功能不只是涉及到数据库。

整个功能包括数据库，消息队列，第三方模块，整个链路是一个大的事务，数据库的事务无法回滚其他层。

解决方案: 只有数据库的事务执行成功了才执行其他层。
