### 2. 使用原则与方法论



#### 2.1 AI 不能替代系统设计

**类型**：原则

一句话描述易制造「开发变容易」的错觉；缺整体设计时逻辑脆弱、技术债高。

- **建议做法**：先定边界、模块划分与数据流，再让 AI 按设计实现局部；避免把整条业务链路压成一句自然语言交付。



#### 2.2 Vibe Coding 宜先探坑再正式设计

**类型**：原则

可先快速试做，把暴露问题作为正式设计输入，而非跳过设计当成品。

- **建议做法**：用短周期试做摸清接口、依赖与边界麻烦，再据此写正式设计并重做或收敛实现；试做产物默认不当作可维护交付。



#### 2.3 人必须监管与决策

**类型**：原则

不追求 AI 不间断自动交付产品；关键决策与验收在人侧。

- **建议做法**：把目标、约束与验收标准写清，分步检查产出；架构取舍、合并与上线等决策由人确认后再继续。



#### 2.4 多次小任务优于一次大包

**类型**：原则

长任务易偏航、易「偷懒」；拆成可验收小步更稳。

- **建议做法**：按可验证结果切任务，每步有明确完成定义；多轮推进并在步间验收，避免一次塞入跨模块大包。



#### 2.5 质量优先于「能跑多久」

**类型**：原则

好 Agent 的标准是符合预期、可维护、成本可控，而非长时间空转。

- **建议做法**：以结果是否达预期、是否可维护、token 与时间成本是否合理为评价；不把「跑得久」当能力指标。相关构想见第 4 章，此处不重复展开。



#### 2.6 资料与知识库重于反复调 Prompt

**类型**：原则

提示词难复用；可复用的是规范、范例与知识库。

- **建议做法**：把稳定约定沉淀为项目级规范、范例与知识库，任务时引用这些资料；少在单次会话里反复打磨不可迁移的提示词。



#### 2.7 看懂 ≠ 会用 ≠ 能讲懂

**类型**：原则

AI 讲解易造成学会错觉；能讲清、能跑通才算内化。

- **建议做法**：学完后用自己的话复述要点，并独立完成一小段实践流程；仅「看懂讲解」不算掌握。



#### 2.8 用陈述补上下文，不用反问纠错

**类型**：原则

「难道不该是…」仍在逼模型猜意图；应明确补充要求与背景。

- **建议做法**：纠错时直接陈述正确期望、约束与背景事实；禁用「难道不该是…」式反问句纠错。



#### 2.9 正向说明优先于堆反向约束

**类型**：原则

尽量写期望行为；过多「不要…」易被淹没。

- **建议做法**：优先描述「应该做成什么样」；必要的反向约束精简列出，避免大段「不要…」清单冲淡主目标。



#### 2.10 先跑通再优化

**类型**：原则

初期以可运行为主，再迭代结构与质量。

- **建议做法**：先打通最小可运行路径并验证正确性，再重构结构、补测试与打磨质量，避免一开始同时追求完美。



#### 2.11 执行要有思维链与原因

**类型**：原则

每个关键操作应能说明为何这样做（「该这么做」）。

- **建议做法**：关键步骤前简要写出原因与依据，再执行；无法说明理由时先停下来澄清，不盲从惯性操作。



#### 2.12 先收集已知条件再切入

**类型**：原则

收集条件 → 找切入点 → 分析 → 澄清 → 方案 → 执行（「该这么做」）。

- **建议做法**：开工前先汇总已知约束、目标与材料，再定切入点与分析路径；有缺口先澄清，再出方案并执行。



### 3. 机制与工具经验



#### 3.1 上下文与记忆



##### 3.1.1 上下文永远不完整

**类型**：经验

未写出的默认理解与动态状态（如 Git），模型不会自动知道，会自行假设。

- **现象 / 场景**：人脑里默认成立的背景、原因与解释通常不会说出口；仓库是否干净、当前分支与未提交变更等动态状态，文档里也很少写全。若未写入上下文，AI 常按「仓库干净、状态自洽」去规划，得到错误 plan。
- **原因 / 机制**：上下文只包含被显式提供的信息；缺失部分由模型猜测补齐，而非从外部持久世界自动同步。
- **建议做法**：把默认理解写成原因与解释；开工前把当前 Git 状态、关键环境事实加载进上下文，再让模型做 plan 或执行。



##### 3.1.2 网页对话 vs Agent 工具的上下文形态

**类型**：经验

网页端近似多轮问答拼接；Agent 工具还含思考、工具调用与命令结果，上下文管理更复杂。

- **现象 / 场景**：网页对话常把聊天记录当作连续的「单次提问 + 回答」拼接；在 Agent 场景中，除对话外还有思考过程、工具调用与命令输出进入请求。
- **原因 / 机制**：形态不同，可观测与可控制的边界也不同；Agent 侧「过程是否整段进入下一次请求」等拼装细节仍需系统学习（见 5.1.2）。
- **建议做法**：网页对话按多轮 Q/A 管理主题与长度；Agent 任务主动控制哪些工具结果进入主上下文，避免过程噪声淹没目标。
- **备注**：此处为形态观察；Agent 工具链如何拼装属学习清单，不在此展开结论。



##### 3.1.3 摘要替换上下文，原始记录另存

**类型**：经验

进上下文的应是摘要；原始聊天宜保留，避免只靠不可逆压缩。

- **现象 / 场景**：长对话需要压缩上下文时，若只留下压缩结果、丢掉原始记录，后续无法回溯细节与决策依据。
- **建议做法**：用摘要替换当前上下文中的冗长历史；原始通信另行保存，摘要与原文双轨，而不是把原始记录压没。



##### 3.1.4 生成内容有「缓存变量」效应

**类型**：经验

用户手改文件后若未让 AI 重读，后续修改可能仍基于旧生成内容。

- **现象 / 场景**：AI 生成 content → 用户手改为 content_ → 再要求调整结构或格式时，模型仍按旧 content 改写，仿佛内存中仍挂着生成时的缓存变量。
- **原因 / 机制**：会话会记住己方生成内容及其位置，以省 token、保连贯；手改发生在模型视野之外，除非重新读取磁盘文件。
- **建议做法**：手改后先让 AI 重读相关文件再继续编辑；尽量少在未同步的前提下交替「人改文件 / AI 改结构」。缓冲准确性与省 token 需取舍。



##### 3.1.5 主会话宜委派，细节交给 Sub-agent

**类型**：经验

上下文紧张时，主对话只分发与验收，细节分析交给 Sub-agent。

- **现象 / 场景**：主会话塞满检索、长文分析与中间结果后，目标与约束被冲淡，后续指令更易偏航。
- **建议做法**：主 agent 负责拆任务、发目标与约束、验收结果；分析与执行细节交给 sub-agent，用摘要回传，保护主会话上下文。



#### 3.2 任务委派与 Agent 结构



##### 3.2.1 分层委派，上层只看摘要

**类型**：经验

Boss 发目标与约束并验收；Worker 执行并回摘要；核心是分层与上下文隔离，而非固定职级层数。

- **现象 / 场景**：把所有细节堆在同一会话，上层既难盯目标，又被过程淹没。
- **建议做法**：上层只下发目标、约束与验收标准，并基于摘要做决策；下层执行后回传结论摘要，不把完整过程默认灌回上层。
- **备注**：实践中可按需要延伸为多层（如 Boss / 中层协调 / Worker），三层结构是可选延伸，不是强制组织图。



##### 3.2.2 不同任务用不同策略

**类型**：经验

不宜一套 Agent 策略打天下；策略应随任务类型变化。

- **现象 / 场景**：探索、实现、格式转换、资料整理等任务对深度思考、工具使用与拆分粒度的要求不同，套同一策略易浪费或欠做。
- **建议做法**：按任务类型选择策略（是否深度推理、是否拆 sub-agent、验收粒度等）；转换类任务可降低不必要的深度思考，复杂实现则加强分步与验收。



##### 3.2.3 执行前先对齐任务理解

**类型**：经验

开工前简短复述目标与步骤，确认理解一致再执行。

- **现象 / 场景**：直接按字面开干时，目标边界、完成定义与步骤顺序常与用户预期不一致。
- **建议做法**：执行前用几句话复述目标、约束、大致步骤与验收点，请用户确认或自我校验后再动手。



##### 3.2.4 Agent 默认被动，需主动补上下文

**类型**：经验

未读全约束与相关材料就开干，容易偏差。

- **现象 / 场景**：Agent 不会默认补齐项目规范、关联文件与 Git 历史；缺上下文时仍会「看起来在推进」。
- **建议做法**：开工前主动加载约束文档、相关文件与必要状态；关键关联由人指定或要求先读再改，不假设模型会自发找全上下文。



#### 3.3 规则、Skill 与提示词



##### 3.3.1 规则会衰减，且会与 Skill 冲突

**类型**：经验

长上下文会冲淡既有规则；强流程类 Skill 也可能覆盖用户约束。

- **现象 / 场景**：会话变长后，早先写明的规则被后续内容淹没；某些 Skill（如 brainstorming 类流程）曾在用户未及时确认时自动推进 commit 等操作。
- **原因 / 机制**：规则与 Skill 同属上下文中的指令源，强度、位置与后续流程会互相覆盖，并非永久硬保证。
- **建议做法**：关键约束在关键步骤前再次点名；对会改仓库状态的 Skill，明确是否允许自动 commit，必要时拆步确认。
- **备注**：自动确认 / 自动 commit 等属曾观察到的产品行为，具体表现可能随版本变化，不宜写成永久保证。



##### 3.3.2 规则有例外，要写清优先级

**类型**：经验

规则、习惯不能写死无例外；例外须说明原因，并保留优先级与决策记录。

- **现象 / 场景**：特殊场景强行套通用规则会误伤正确做法；事后说不清为何破例，规则体系会失信。
- **建议做法**：通用规则与例外场景分开写；例外附原因；约定规则 / 约束 / 习惯的优先级，并用决策记录留痕。



##### 3.3.3 Skill 宜通用，勿绑定单次会话状态

**类型**：经验

Skill 过贴当前仓库或瞬时上下文，换会话即失效。

- **现象 / 场景**：创建 Skill 时写进「当前分支、当前文件列表、本次临时约定」等瞬时状态，下次会话环境一变就不可用。
- **建议做法**：Skill 写可迁移的目标、步骤与检查点；瞬时路径、会话专属状态作为调用时的变量输入，不写进 Skill 本体。



##### 3.3.4 Skill 要区分常量与变量

**类型**：经验

写 Skill 时明确固定项与可变输入，并做效果测试。

- **现象 / 场景**：常量与变量混写会导致调用时该改的改不动、不该变的被冲掉；未测试则边界行为未知。
- **建议做法**：先标清常量（流程、质量标准）与变量（路径、参数、材料）；写完后像测代码一样做效果测试，再投入使用。



##### 3.3.5 用边界用例检验 Prompt/Skill

**类型**：经验

用类似「1 杯 / 99 杯 / 蛋炒饭」的边界用例，检验的是提示词或 Skill 的覆盖与稳定性，而非「token 是否优秀」。

- **现象 / 场景**：只按典型路径写 Prompt/Skill 时，极端数量、无关请求等边界会暴露漏洞；把问题归咎于「token」会误导优化方向。
- **建议做法**：像代码测试一样设计边界与异常输入（正常量、超量、无关任务等），用结果反推 Prompt/Skill 是否需补全分支，而不是评价单次 token。
- **备注**：原文中「判断 token」的表述，此处按澄清结论改为检验提示词或 Skill。



##### 3.3.6 小概率场景用事后检查，不塞常驻规则

**类型**：经验

极低频、场景绑定的失败，适合任务后检查，不宜塞进常驻 Prompt。

- **现象 / 场景**：Python 中 f-string 换行与 `"-" * n` 一类乘法拼接不当，曾导致大段内容被重复刷屏；属特定写法下的小概率问题。
- **建议做法**：完成后做一次针对性 check；不要为每个小概率坑增加常驻规则，以免规则膨胀、主目标被冲淡。
- **备注**：错误形态示意（说明作用域问题即可，非完整复现）：

```python
# 错误形态示意：乘法作用域与 f-string 拼接不当，可能导致大段内容被重复
f"content\n\n"
f"-" * 30 + f"\n\ncontent"
```



##### 3.3.7 格式转换：外层勿套代码块；可脚本+AI 润色

**类型**：经验

长文转 Markdown 时外层勿再套代码块；HTML→md 可脚本先行再 AI 润色；纯靠 AI 转 PDF 质量差。

- **现象 / 场景**：多模型在长内容转 md 时，时而整段进代码块、时而直接输出，格式混乱；HTML 结构适合机械抽取；PDF 版式复杂，纯模型转换结果往往不可用。
- **建议做法**：要求「直接输出内容，最外层不要套代码块」；HTML→md 先写脚本抽取，再让 AI 补代码块与样式；PDF 优先可靠抽取链路，不依赖单次纯 AI 转换。
- **备注**：格式转换类任务通常不需要过深的推理，重点是输出形态稳定。



##### 3.3.8 文科资料整理慎用 AI 编造与脚本替换

**类型**：经验

文科资料易被模型脱离原文编造；多轮正则/脚本替换易误匹配且难回滚。

- **现象 / 场景**：让 AI 整理人文类材料时，易补写原文没有的表述；用 Agent 写脚本做多轮批量替换时，匹配过宽会改错，且难以逐步回退。
- **建议做法**：以原文为准，禁止无依据扩写；需要批量改写时优先可审阅、可回滚的流程，慎用多轮盲目正则替换；重要材料先备份再改。



#### 3.4 Claude Code 与配置管理



##### 3.4.1 ignore 的文件也可能被插件强行纳入 Git

**类型**：经验

已被 ignore 的路径，仍可能被插件或自动化流程写回 Git 追踪。

- **现象 / 场景**：曾观察到某些插件或流程（如 superpower 一类）自动把工作记录文档加入仓库追踪，即使相关路径本在 ignore 中。
- **原因 / 机制**：ignore 约束的是常规工作流；插件侧若自行 `git add` 或改写状态，可绕过用户对 ignore 的预期。
- **建议做法**：对会改仓库状态的插件与 Skill 保持警惕；关键提交前检查 `git status`，确认未把应忽略的工作记录或临时文档带进提交。
- **备注**：属曾观察到的产品/插件行为，具体表现可能随版本变化，不宜写成永久保证。



##### 3.4.2 仓库 ignore 配置文件会导致多分支配置混乱

**类型**：经验

把 Claude Code 等工具配置文件整体 ignore 后，各分支间配置易不一致、难同步。

- **现象 / 场景**：仓库 ignore 了 Claude Code 相关配置后，切换分支时本地配置与分支预期脱节，出现多分支配置混乱。
- **原因 / 机制**：配置若既不进版本库、又无明确同步机制，每个分支/工作区各自漂移，无法以仓库为单一事实来源。
- **建议做法**：需要跨分支一致的配置应纳入版本管理，或建立明确的项目级同步方式；不要默认「全部 ignore 配置文件」。



##### 3.4.3 CLAUDE.md 放稳定说明，不放具体任务清单

**类型**：经验

CLAUDE.md 应承载目录结构与固定约定；具体任务另文件管理。

- **现象 / 场景**：把当前任务清单写进 CLAUDE.md 后，任务一变就要改常驻说明，既污染稳定上下文，也易与一次性任务混淆。
- **建议做法**：CLAUDE.md 只写目录说明、固定约定与特殊文件约定；具体任务放到专门任务文件或会话指令中，不塞进 CLAUDE.md 本体。



##### 3.4.4 配置集中管理，且按项目区分

**类型**：经验

配置宜集中在清晰目录，并按**项目级**区分目标与要求。

- **现象 / 场景**：不同项目目标不同，配置散落各处时难维护，也容易把某一项目的约定误用到另一项目。
- **建议做法**：把配置集中到明确目录统一管理；每个项目维护自己的配置与约定，不假设跨项目可原样复用同一套细节。



##### 3.4.5 Memory 与规范采用项目级

**类型**：经验

Memory 与开发规范一律采用**项目级**；**禁止依赖全局统一规范**；不同项目可以、也应当有不同要求。

- **现象 / 场景**：若只依赖用户全局 Memory 或一套「万能」规范，换项目后约束错位，模型按错误默认推进；工具侧也可能默认加载 User 级 Memory 而忽略项目约定。
- **原因 / 机制**：项目边界、目录习惯、提交规范与验收标准并不相同；全局统一规范无法覆盖项目差异，却容易造成「已统一」的错觉。
- **建议做法**：在项目内维护 Memory、规范与约定，任务时优先加载本项目资料；明确禁止把全局统一规范当作唯一依据；跨项目提炼时保留各项目原始数据，再整理可迁移的通用部分。



#### 3.5 编码、文档与维护策略



##### 3.5.1 AI 偏事后修 bug，缺预防式设计

**类型**：经验

AI 默认常在问题暴露后才修补；健壮性、边界与预防需人主动补上。

- **现象 / 场景**：实现看似能跑，却缺边界与失败路径；问题爆发后再修 bug，技术债与维护成本迅速升高。
- **原因 / 机制**：默认行为偏向「出了问题再改」，而非在设计阶段枚举风险与预防措施。
- **建议做法**：人在设计与验收时补健壮性、边界条件与预防策略；要求实现覆盖关键失败路径，而不是只修已复现的报错。



##### 3.5.2 改代码前要能定位结构与标识

**类型**：经验

说不清改哪一处、缺少稳定路径或 id 时，改动结果不稳定。

- **现象 / 场景**：对代码结构不熟、无法命名目标模块时，只能用模糊自然语言描述，模型难以精确定位修改点。
- **建议做法**：改前先定位结构与稳定标识（路径、符号、组件 id 等），能指出「改哪里」再下指令；定位不清时先读代码或让 AI 先做结构梳理，再动手改。



##### 3.5.3 数据获取类逻辑易前后不一致

**类型**：经验

数据获取（尤其爬虫）中，何时用何数据、何时可得何数据，模型逻辑易前后矛盾。

- **现象 / 场景**：改爬虫或数据管道时，阶段依赖与数据可用性未写清，前后步骤对「已有字段 / 可抓取时机」假设不一致。
- **建议做法**：显式说明各阶段输入输出、数据来源与可用性约束；改数据获取逻辑时要求对齐全链路假设，避免只改局部步骤。



##### 3.5.4 分散维护优于一次性大重构

**类型**：经验

不强制一次性大重构；碰到相关文件再顺手维护，并区分通用规范与特殊要求。

- **现象 / 场景**：让 AI 一次性大范围重构，范围失控、回归面大；积累经验时又把场景特例误写成普适规范。
- **建议做法**：遇到问题再修、调整到该文件时顺手维护（分散维护）；沉淀时区分通用规范与项目/场景特殊要求，特殊需求不要硬塞成全局规则。



##### 3.5.5 维护宜挂在读取任务上

**类型**：经验

少开纯维护会话；读文档办事时对照清单顺带维护，更省 token、更可复用上下文。

- **现象 / 场景**：专门开一轮「只做维护」会加载大量内容，维护完即结束，后续任务难以复用这批上下文，token 性价比低。
- **建议做法**：在读取文档执行业务任务时，对照维护清单顺带检查与修正；减少独立的纯维护会话，把维护挂在有实际产出的读取路径上。
- **备注**：可将该约定写进项目级 CLAUDE.md 或维护清单，便于反复引用。



##### 3.5.6 文档有过时风险，关键结论需二次确认

**类型**：经验

文档会过时；规范、接口、配置类关键结论使用前应二次确认。

- **现象 / 场景**：按旧文档实现接口或配置后，发现与当前代码/环境不符。
- **建议做法**：关键结论以现行代码、配置与实测为准，文档仅作线索；规范、接口与配置类信息在采用前再核对一遍。



##### 3.5.7 长文本任务易忘规则：先备份再改

**类型**：经验

处理长文本时容易遗忘既有规则；编辑前先 Copy 备份。

- **现象 / 场景**：长文编辑轮次多，约束与格式规则易被冲淡，一旦误改难回退。
- **建议做法**：动手改长文本前先复制备份；关键规则在编辑前再次点名，改完做一次针对性检查。



##### 3.5.8 AI 不主动关联相关文件与 Git 历史

**类型**：经验

写代码时模型不会默认找齐相关文件、Git 历史与他人进度；协作上下文需人指定。

- **现象 / 场景**：未指明关联模块、提交历史或协作约定时，AI 只在局部文件内改，忽略同步进度与团队处境。
- **建议做法**：手动指定相关文件、必要 Git 历史与协作约束；需要与他人对齐的思路与进度由人写入上下文，不假设模型会主动同步。



##### 3.5.9 前端可先 Demo 组件、先设计后实现

**类型**：经验

前端可先搭测试 Demo，按组件搭建 UI 结构，再进入实现。

- **现象 / 场景**：一上来就写业务实现时，组件边界与页面结构未定，返工多。
- **建议做法**：先生成测试 Demo 页，一个组件一个组件搭建；先当 UI 设计师定结构，再切换为前端实现，形成可复用的 AI 前端工作流片段。



#### 3.6 用 AI 学习



##### 3.6.1 给目标让 AI 提问，人学问题链

**类型**：经验

给定学习目标后，让 AI 自行提问并整理问答，人吸收整条问题链，而不是只看最终答案。

- **现象 / 场景**：直接要讲解或答案时，缺少「会问什么」的过程，难以形成可迁移的学习路径。
- **建议做法**：明确学习目标，要求 AI 模拟学习过程：提出问题 → 整理回答 → 形成问题链；人重点吸收提问路径与整理后的问答，而不是只背结论。



##### 3.6.2 讲解要达到能运用

**类型**：经验

讲解目标是能讲清、能跑通、能运用；仅「看懂输出」不够（与 2.7 呼应）。

- **现象 / 场景**：AI 讲解流畅时易产生「已经会了」的错觉，实际既讲不清也用不出来。
- **建议做法**：听完讲解后用自己的话复述，并独立完成一小段实践；以能运用为验收，不以看懂讲解为终点。



##### 3.6.3 先让 AI 加载开发经验/规范再写代码

**类型**：经验

写代码前先加载项目开发经验与规范，把范式作为前置上下文。

- **现象 / 场景**：未加载规范就直接生成代码，风格与约束漂移，后续再补规范成本高。
- **建议做法**：实现前先让 AI 读取项目级开发规范、范例与相关经验，再按约定写代码；规范当前置条件，而非事后补丁。



##### 3.6.4 可从优秀开源项目提炼开发范式

**类型**：经验

可让 AI 总结优秀开源项目的结构与流程，沉淀为可复用的开发规范。

- **现象 / 场景**：凭空要「最佳实践」易空泛；对照具体优秀项目更容易抽出可落地的结构与流程。
- **建议做法**：选定参考开源项目，让 AI 总结目录结构、模块边界与开发流程，提炼为项目可用的开发范式与规范后再运用。



### 4. 产品与工作流构想



#### 4.1 交互与角色



##### 4.1.1 反思 Agent

**类型**：构想  
**状态**：未验证

专责补上下文、质疑偏差，模拟主动打磨交付物的后台角色。

- **设想**：当前 Agent 多为被动一问一答，缺少「优秀同学」式的主观能动性——主动补齐未言明的上下文、质疑明显偏差、在交付前自行打磨质量。反思 Agent 作为并行或后置角色，对主 Agent 的 plan 与产出做复核：检查是否遗漏约束、是否需要更多材料、结论是否可维护；将补全建议与质量问题回传主流程或用户，而不是等用户指出后再改。
- **备注**：与 3.2.4（默认被动、需主动补上下文）、2.5（质量优先）呼应；本条为产品形态构想，原则本身见第 2 章。



##### 4.1.2 Asker 智能体 + 前端表单

**类型**：构想  
**状态**：未验证

由专用智能体生成待确认问题，经前端表单收集答案，减少含糊多轮对话。

- **设想**：开工或澄清阶段，Asker 根据任务缺口列出结构化问题（必填/可选、单选/多选/短答），渲染为表单；用户一次性填完后回注主会话。避免「猜一句、改一句」的碎片澄清，也降低口头答复遗漏字段的概率。
- **备注**：可与 4.1.3 项目经理 Skill 衔接：PM 定需求边界，Asker 负责缺口问题收集。



##### 4.1.3 项目经理 Skill

**类型**：构想  
**状态**：未验证

把自然语言诉求转成专业需求，执行侧疑问统一经 PM 向用户澄清。

- **设想**：用户用口语描述目标后，PM Skill 输出边界清晰的需求说明（目标、约束、验收、非目标）；下游执行 Agent 遇到歧义不直接打断用户，而是汇总疑问交 PM，由 PM 整理后再问用户，保证问题有序、表述专业。
- **备注**：与 4.1.4 多角色协作配套，PM 作为人与多角色之间的对齐枢纽。



##### 4.1.4 多角色协作

**类型**：构想  
**状态**：未验证

前后端等角色分工协作，经项目经理角色与用户对齐。

- **设想**：按任务需要实例化前端、后端、测试等角色 Agent，各自在职责范围内产出；跨角色冲突与对用户的提问统一经 PM 汇聚，避免多头同时追问用户。角色间用摘要与接口约定通信，而非共享完整过程上下文。
- **备注**：分层与摘要上报见 3.2.1；本条侧重「多专业角色 + PM 对齐用户」的产品形态。



##### 4.1.5 Agent 聊天室

**类型**：构想  
**状态**：未验证

多 Agent 群聊协作，并将对话与决策记录持久化。

- **设想**：提供类似群聊的界面与会话模型，多个 Agent（及用户）在同一话题下发言、@ 指定角色；关键结论、分歧与决议写入可检索记录，便于事后回溯与复用，而不是散落在互不可见的独立会话里。
- **备注**：持久化形态可与 4.3.1 记忆可视化联动。



#### 4.2 教程与知识生产



##### 4.2.1 傻子提问者

**类型**：构想  
**状态**：未验证

以零基础角色持续追问教程，逼迫讲解补全跳跃与未定义概念。

- **设想**：在生成或审阅教程时，引入「傻子」角色：对每一个新术语、隐含步骤与未交代前提发问，直到讲解在零基础上也可跟读。用外部压力暴露作者/模型默认读者「已经知道」的缺口。
- **备注**：与 4.2.2 写书式讲解配套使用：提问者找洞，写稿人按规范补洞与定稿。



##### 4.2.2 写书式讲解 / 写稿人

**类型**：构想  
**状态**：未验证

章节连贯、新概念必先解释、已讲内容用引用回指；由写稿人角色决定是否补写。

- **设想**：教程写作按「写书」标准：前后章节语气与术语一致；首次出现的概念必须定义；后文引用前文时标明出处而非重复糊写。写稿人角色在通读草稿后判断哪里缺章、哪里可引用，决定补写还是回链，避免既跳跃又啰嗦。
- **备注**：与 4.2.1 傻子提问者配套；学习侧验收仍可对照 2.7 / 3.6.2（能讲清、能运用）。



##### 4.2.3 自动补上下文 Skill

**类型**：构想  
**状态**：未验证

把人脑中的默认理解结构化写出，再作为上下文喂给模型。

- **设想**：在任务启动时触发 Skill：引导用户或从项目文档中抽取「默认成立」的背景、约束与术语，整理成固定结构（目标、环境、禁忌、已有材料等）写入会话或附件，再进入正式执行，减少模型对未言明默认值的猜测。
- **备注**：针对 3.1.1、3.2.4 所观察的缺口；方法原则「先收集已知条件」见 2.12，此处不展开。



##### 4.2.4 讲解 Skill 使用示例的 Skill

**类型**：构想  
**状态**：未验证

元技能：示范如何正确调用与组合其他 Skill。

- **设想**：用户面对多个 Skill 不知何时用、如何填变量时，由该元技能根据任务类型给出调用示例、参数说明与反例（误用场景），降低 Skill 文档只写规范、缺少「怎么用」的成本。
- **备注**：与 3.3.3、3.3.4（Skill 通用性、常量/变量）相关，侧重教学与示例生产。



##### 4.2.5 创建标签 Skill

**类型**：构想  
**状态**：未验证

根据内容描述自动生成可用的分类标签。

- **设想**：输入一段笔记、文档或任务摘要，Skill 输出候选标签（层级、同义合并建议、是否已有体系内标签），便于归档进目录标签树或检索系统，减少人工想标签名的摩擦。
- **备注**：输出应尽量对齐项目既有标签体系，而非每次发明全新命名。



##### 4.2.6 母技能 → 场景化子技能

**类型**：构想  
**状态**：未验证

由通用母版 Skill 派生出绑定具体场景的子技能。

- **设想**：先维护一套稳定的母技能（流程骨架、质量标准、检查点），再按场景（某项目、某文档类型、某工具链）实例化子技能：继承母版常量，只替换场景变量与示例。更新母版时可批量提示子技能同步，避免每个场景各写一套互不兼容的流程。
- **备注**：与 3.3.3、3.3.4 的常量/变量划分一致；实现时需验证派生与同步成本。



#### 4.3 记忆、话题与工作流可视化



##### 4.3.1 记忆可视化与可编辑

**类型**：构想  
**状态**：未验证

记忆条目可查看、可编辑，并带有对话或来源属性。

- **设想**：将 Memory 从黑盒列表改为可视化面板：展示条目内容、来源会话、写入时间与作用范围（项目级等）；用户可直接改写、停用或合并条目，使「模型记住了什么」可审计、可纠正。
- **备注**：记忆层级坚持项目级（见 3.4.5），可视化不改变「禁止依赖全局统一规范」的原则。



##### 4.3.2 话题策略型智能体

**类型**：构想  
**状态**：未验证

单话题会话携带并持续更新「话题头」，作为该话题的策略摘要。

- **设想**：每个话题维护一个简短话题头（目标、当前阶段、关键约束、未决问题）；轮次推进时更新话题头，新消息与子任务优先对齐话题头，减少长对话中主题漂移与重复澄清。
- **备注**：可与 3.1.3（摘要进上下文、原文另存）配合：话题头即面向执行的活摘要。



##### 4.3.3 猜测隐形大话题

**类型**：构想  
**状态**：未验证

从零散小问题推断用户背后的大框架，并显式提出供确认。

- **设想**：当用户连续提出看似零碎的问题时，Agent 尝试归纳「可能的大话题 / 总目标」，以假设形式展示给用户确认或修正；确认后按大框架组织后续步骤与资料，而不是一直在局部打补丁。
- **备注**：猜测必须可被用户否定；未确认前不当作既定需求执行。



##### 4.3.4 Agent 工作流看板

**类型**：构想  
**状态**：未验证

可视化展示 plan 步骤、角色分工与当前状态。

- **设想**：将任务 plan 渲染为看板（待办 / 进行中 / 阻塞 / 完成），标注负责角色、依赖与验收点；用户可在看板上调整优先级或卡住某步，而不是只在聊天流里翻历史找进度。
- **备注**：与 3.2.1 分层委派、4.1.4 多角色协作互补，侧重「看得见的流程」。



##### 4.3.5 工作流伪代码 → 工作树

**类型**：构想  
**状态**：未验证

用类语法树结构执行工作流，中间过程以文字描述可观察。

- **设想**：将流程写成可读的伪代码或 DSL，解析为工作树节点（顺序、分支、循环、并行）；执行时沿树推进，每节点输出简短文字说明「当前在做什么、结果如何」，便于调试与回放，而不是黑盒一口气跑完。
- **备注**：与 4.3.4 看板可共用同一 plan 源；节点级说明呼应「关键操作要有原因」（原则见 2.11），此处不展开原则本身。



##### 4.3.6 用户纠正行为持久化

**类型**：构想  
**状态**：未验证

把用户纠正过的行为写入记忆，形成可复用的自进化约束。

- **设想**：当用户明确纠正 Agent 的某类做法时，系统提炼为可检索规则（场景 + 错误行为 + 正确期望），写入项目级记忆；后续同类任务自动加载，减少同一错误反复犯、用户反复说。
- **备注**：写入前宜确认提炼是否准确；与 4.3.1 可编辑记忆、3.3.2 规则例外与优先级相关。



##### 4.3.7 从多 Skill 提取用户习惯

**类型**：构想  
**状态**：未验证

归纳用户在多个 Skill 中的常用规则，并可视化管理。

- **设想**：扫描用户常用 Skill 与历史调用，提取反复出现的偏好（命名、提交习惯、文档结构、验收粒度等），汇总为「习惯画像」面板，供启用/禁用与按项目裁剪，避免习惯只散落在各 Skill 正文里无法统一调整。
- **备注**：提取结果默认项目级或可导出片段；跨项目提炼时保留原始再归纳（参见 5.4.2 思路，本章不展开待办）。



#### 4.4 工具链与辅助能力



##### 4.4.1 Shell + Monitor 异步执行

**类型**：构想  
**状态**：未验证

Shell 负责执行命令；Monitor 盯任务结束并 callback，避免主流程阻塞空等。

- **设想**：长时命令由 Shell 异步拉起，主 Agent 不阻塞在单次工具返回上；Monitor 观察进程或任务状态，结束后以 callback 唤醒后续步骤（汇总输出、触发下一阶段或通知用户）。适用于构建、测试、下载等耗时长、结果可延后处理的场景。
- **备注**：属工具链机制构想；评价标准仍以结果质量与成本为准（见 2.5），不以「挂得久」为目标。



##### 4.4.2 提示词安全

**类型**：构想  
**状态**：未验证

针对注入、回显原文与越权指令等风险的防护能力。

- **设想**：在提示词与外部内容进入模型前做安全层：检测并隔离可疑注入、限制「复述系统提示 / 泄露密钥」类请求、对不可信资料采用沙箱式引用。目标是降低工具链被恶意或误粘贴内容带偏的概率。
- **备注**：未验证具体检测策略与误杀率，实施前需单独设计与评测。



##### 4.4.3 语音输入 + Prompt Optimizer

**类型**：构想  
**状态**：未验证

口语输入后经优化器整理为可用提示词再交给执行模型。

- **设想**：用户语音转写为粗糙文本后，先进入 Prompt Optimizer：补全结构、去掉口头禅、标出目标/约束/材料，输出清晰提示词再启动任务，降低「边想边说」导致的指令残缺。
- **备注**：可与 4.4.4 脱敏、4.4.5 打磨器串成流水线。



##### 4.4.4 Prompt Optimizer 脱敏

**类型**：构想  
**状态**：未验证

对隐私与敏感字段处理后，再送入提示词优化流程。

- **设想**：优化前提取并掩码姓名、密钥、内部 URL、未公开业务数据等，用占位符替换；优化完成后再按策略决定是否在本地回填。避免为了「写好 prompt」把敏感原文送进不可控环节。
- **备注**：与 4.4.3 配套；脱敏规则应可按项目配置。



##### 4.4.5 提示词打磨器

**类型**：构想  
**状态**：未验证

多轮打磨提示词，并保留修改记录与输出对比。

- **设想**：提供专用打磨会话：每一版提示词与对应试跑输出并排对比，记录改了什么、效果如何；支持回退到历史版本，避免在主任务会话里无痕改 prompt 导致不可复现。
- **备注**：打磨产物可沉淀为项目范例（呼应 2.6：资料重于反复调不可迁移的 prompt）。



##### 4.4.6 探索模式

**类型**：构想  
**状态**：未验证

允许模型在约束内自主推断与探索，而不只套用既有经验模板。

- **设想**：对开放式调研、方案比较、未知代码库摸底等任务，显式开启探索模式：鼓励提出假设、小步试探与记录否证，而不是强行套「标准三步」或过早收敛。探索结束需输出假设、证据与未决问题清单。
- **备注**：与 2.2（先探坑再设计）、2.4（小步可验收）相容；探索不等于无验收空转（见 2.5）。



##### 4.4.7 快速选型包

**类型**：构想  
**状态**：未验证

技术栈、Skill、经验条目与配置说明的快速组合包。

- **设想**：按场景（如「文档站 + Markdown 规范」「前端 Demo 工作流」）预制选型包：推荐工具/栈、配套 Skill 列表、相关经验条目链接、项目级配置模板。新开同类项目时一键或一指令装载，缩短从零拼装上下文的时间。
- **备注**：包内容必须可裁剪；仍坚持项目级配置，不强制全局统一包（见 3.4.5）。



##### 4.4.8 Agent 选 Skill 多轮确认

**类型**：构想  
**状态**：未验证

选择调用哪些 Skill 时至少经过两轮推理与确认，再锁定方案。

- **设想**：首轮根据任务列出候选 Skill 与理由；次轮对照约束、互斥关系与成本做删减或替换，必要时请用户确认后再执行。避免「名字像就调用」或一次点名多个冲突 Skill。
- **备注**：与 3.3.1（规则与 Skill 冲突）、3.2.3（执行前对齐理解）相关；两轮为最低设想，复杂任务可更多。
