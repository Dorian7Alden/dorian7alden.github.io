### 2. 使用原则与方法论



#### 2.1 AI 不能替代系统设计

**类型**：原则

一句话描述易制造「开发变容易」的错觉；缺整体设计时逻辑脆弱、技术债高。

- **建议做法**：先定边界、模块划分与数据流，再让 AI 按设计实现局部；避免把整条业务链路压成一句自然语言交付。



#### 2.2 Vibe Coding 宜先探坑再正式设计

**类型**：原则

可先快速试做，把暴露问题作为正式设计输入，而非跳过设计当成品。

- **建议做法**：用短周期试做摸清接口、依赖与边界麻烦，再据此写正式设计并重做或收敛实现；试做产物默认不当作可维护交付。



#### 2.3 人必须监管与决策

**类型**：原则

不追求 AI 不间断自动交付产品；关键决策与验收在人侧。

- **建议做法**：把目标、约束与验收标准写清，分步检查产出；架构取舍、合并与上线等决策由人确认后再继续。



#### 2.4 多次小任务优于一次大包

**类型**：原则

长任务易偏航、易「偷懒」；拆成可验收小步更稳。

- **建议做法**：按可验证结果切任务，每步有明确完成定义；多轮推进并在步间验收，避免一次塞入跨模块大包。



#### 2.5 质量优先于「能跑多久」

**类型**：原则

好 Agent 的标准是符合预期、可维护、成本可控，而非长时间空转。

- **建议做法**：以结果是否达预期、是否可维护、token 与时间成本是否合理为评价；不把「跑得久」当能力指标。相关构想见第 4 章，此处不重复展开。



#### 2.6 资料与知识库重于反复调 Prompt

**类型**：原则

提示词难复用；可复用的是规范、范例与知识库。

- **建议做法**：把稳定约定沉淀为项目级规范、范例与知识库，任务时引用这些资料；少在单次会话里反复打磨不可迁移的提示词。



#### 2.7 看懂 ≠ 会用 ≠ 能讲懂

**类型**：原则

AI 讲解易造成学会错觉；能讲清、能跑通才算内化。

- **建议做法**：学完后用自己的话复述要点，并独立完成一小段实践流程；仅「看懂讲解」不算掌握。



#### 2.8 用陈述补上下文，不用反问纠错

**类型**：原则

「难道不该是…」仍在逼模型猜意图；应明确补充要求与背景。

- **建议做法**：纠错时直接陈述正确期望、约束与背景事实；禁用「难道不该是…」式反问句纠错。



#### 2.9 正向说明优先于堆反向约束

**类型**：原则

尽量写期望行为；过多「不要…」易被淹没。

- **建议做法**：优先描述「应该做成什么样」；必要的反向约束精简列出，避免大段「不要…」清单冲淡主目标。



#### 2.10 先跑通再优化

**类型**：原则

初期以可运行为主，再迭代结构与质量。

- **建议做法**：先打通最小可运行路径并验证正确性，再重构结构、补测试与打磨质量，避免一开始同时追求完美。



#### 2.11 执行要有思维链与原因

**类型**：原则

每个关键操作应能说明为何这样做（「该这么做」）。

- **建议做法**：关键步骤前简要写出原因与依据，再执行；无法说明理由时先停下来澄清，不盲从惯性操作。



#### 2.12 先收集已知条件再切入

**类型**：原则

收集条件 → 找切入点 → 分析 → 澄清 → 方案 → 执行（「该这么做」）。

- **建议做法**：开工前先汇总已知约束、目标与材料，再定切入点与分析路径；有缺口先澄清，再出方案并执行。



### 3. 机制与工具经验



#### 3.1 上下文与记忆



##### 3.1.1 上下文永远不完整

**类型**：经验

未写出的默认理解与动态状态（如 Git），模型不会自动知道，会自行假设。

- **现象 / 场景**：人脑里默认成立的背景、原因与解释通常不会说出口；仓库是否干净、当前分支与未提交变更等动态状态，文档里也很少写全。若未写入上下文，AI 常按「仓库干净、状态自洽」去规划，得到错误 plan。
- **原因 / 机制**：上下文只包含被显式提供的信息；缺失部分由模型猜测补齐，而非从外部持久世界自动同步。
- **建议做法**：把默认理解写成原因与解释；开工前把当前 Git 状态、关键环境事实加载进上下文，再让模型做 plan 或执行。



##### 3.1.2 网页对话 vs Agent 工具的上下文形态

**类型**：经验

网页端近似多轮问答拼接；Agent 工具还含思考、工具调用与命令结果，上下文管理更复杂。

- **现象 / 场景**：网页对话常把聊天记录当作连续的「单次提问 + 回答」拼接；在 Agent 场景中，除对话外还有思考过程、工具调用与命令输出进入请求。
- **原因 / 机制**：形态不同，可观测与可控制的边界也不同；Agent 侧「过程是否整段进入下一次请求」等拼装细节仍需系统学习（见 5.1.2）。
- **建议做法**：网页对话按多轮 Q/A 管理主题与长度；Agent 任务主动控制哪些工具结果进入主上下文，避免过程噪声淹没目标。
- **备注**：此处为形态观察；Agent 工具链如何拼装属学习清单，不在此展开结论。



##### 3.1.3 摘要替换上下文，原始记录另存

**类型**：经验

进上下文的应是摘要；原始聊天宜保留，避免只靠不可逆压缩。

- **现象 / 场景**：长对话需要压缩上下文时，若只留下压缩结果、丢掉原始记录，后续无法回溯细节与决策依据。
- **建议做法**：用摘要替换当前上下文中的冗长历史；原始通信另行保存，摘要与原文双轨，而不是把原始记录压没。



##### 3.1.4 生成内容有「缓存变量」效应

**类型**：经验

用户手改文件后若未让 AI 重读，后续修改可能仍基于旧生成内容。

- **现象 / 场景**：AI 生成 content → 用户手改为 content_ → 再要求调整结构或格式时，模型仍按旧 content 改写，仿佛内存中仍挂着生成时的缓存变量。
- **原因 / 机制**：会话会记住己方生成内容及其位置，以省 token、保连贯；手改发生在模型视野之外，除非重新读取磁盘文件。
- **建议做法**：手改后先让 AI 重读相关文件再继续编辑；尽量少在未同步的前提下交替「人改文件 / AI 改结构」。缓冲准确性与省 token 需取舍。



##### 3.1.5 主会话宜委派，细节交给 Sub-agent

**类型**：经验

上下文紧张时，主对话只分发与验收，细节分析交给 Sub-agent。

- **现象 / 场景**：主会话塞满检索、长文分析与中间结果后，目标与约束被冲淡，后续指令更易偏航。
- **建议做法**：主 agent 负责拆任务、发目标与约束、验收结果；分析与执行细节交给 sub-agent，用摘要回传，保护主会话上下文。



#### 3.2 任务委派与 Agent 结构



##### 3.2.1 分层委派，上层只看摘要

**类型**：经验

Boss 发目标与约束并验收；Worker 执行并回摘要；核心是分层与上下文隔离，而非固定职级层数。

- **现象 / 场景**：把所有细节堆在同一会话，上层既难盯目标，又被过程淹没。
- **建议做法**：上层只下发目标、约束与验收标准，并基于摘要做决策；下层执行后回传结论摘要，不把完整过程默认灌回上层。
- **备注**：实践中可按需要延伸为多层（如 Boss / 中层协调 / Worker），三层结构是可选延伸，不是强制组织图。



##### 3.2.2 不同任务用不同策略

**类型**：经验

不宜一套 Agent 策略打天下；策略应随任务类型变化。

- **现象 / 场景**：探索、实现、格式转换、资料整理等任务对深度思考、工具使用与拆分粒度的要求不同，套同一策略易浪费或欠做。
- **建议做法**：按任务类型选择策略（是否深度推理、是否拆 sub-agent、验收粒度等）；转换类任务可降低不必要的深度思考，复杂实现则加强分步与验收。



##### 3.2.3 执行前先对齐任务理解

**类型**：经验

开工前简短复述目标与步骤，确认理解一致再执行。

- **现象 / 场景**：直接按字面开干时，目标边界、完成定义与步骤顺序常与用户预期不一致。
- **建议做法**：执行前用几句话复述目标、约束、大致步骤与验收点，请用户确认或自我校验后再动手。



##### 3.2.4 Agent 默认被动，需主动补上下文

**类型**：经验

未读全约束与相关材料就开干，容易偏差。

- **现象 / 场景**：Agent 不会默认补齐项目规范、关联文件与 Git 历史；缺上下文时仍会「看起来在推进」。
- **建议做法**：开工前主动加载约束文档、相关文件与必要状态；关键关联由人指定或要求先读再改，不假设模型会自发找全上下文。



#### 3.3 规则、Skill 与提示词



##### 3.3.1 规则会衰减，且会与 Skill 冲突

**类型**：经验

长上下文会冲淡既有规则；强流程类 Skill 也可能覆盖用户约束。

- **现象 / 场景**：会话变长后，早先写明的规则被后续内容淹没；某些 Skill（如 brainstorming 类流程）曾在用户未及时确认时自动推进 commit 等操作。
- **原因 / 机制**：规则与 Skill 同属上下文中的指令源，强度、位置与后续流程会互相覆盖，并非永久硬保证。
- **建议做法**：关键约束在关键步骤前再次点名；对会改仓库状态的 Skill，明确是否允许自动 commit，必要时拆步确认。
- **备注**：自动确认 / 自动 commit 等属曾观察到的产品行为，具体表现可能随版本变化，不宜写成永久保证。



##### 3.3.2 规则有例外，要写清优先级

**类型**：经验

规则、习惯不能写死无例外；例外须说明原因，并保留优先级与决策记录。

- **现象 / 场景**：特殊场景强行套通用规则会误伤正确做法；事后说不清为何破例，规则体系会失信。
- **建议做法**：通用规则与例外场景分开写；例外附原因；约定规则 / 约束 / 习惯的优先级，并用决策记录留痕。



##### 3.3.3 Skill 宜通用，勿绑定单次会话状态

**类型**：经验

Skill 过贴当前仓库或瞬时上下文，换会话即失效。

- **现象 / 场景**：创建 Skill 时写进「当前分支、当前文件列表、本次临时约定」等瞬时状态，下次会话环境一变就不可用。
- **建议做法**：Skill 写可迁移的目标、步骤与检查点；瞬时路径、会话专属状态作为调用时的变量输入，不写进 Skill 本体。



##### 3.3.4 Skill 要区分常量与变量

**类型**：经验

写 Skill 时明确固定项与可变输入，并做效果测试。

- **现象 / 场景**：常量与变量混写会导致调用时该改的改不动、不该变的被冲掉；未测试则边界行为未知。
- **建议做法**：先标清常量（流程、质量标准）与变量（路径、参数、材料）；写完后像测代码一样做效果测试，再投入使用。



##### 3.3.5 用边界用例检验 Prompt/Skill

**类型**：经验

用类似「1 杯 / 99 杯 / 蛋炒饭」的边界用例，检验的是提示词或 Skill 的覆盖与稳定性，而非「token 是否优秀」。

- **现象 / 场景**：只按典型路径写 Prompt/Skill 时，极端数量、无关请求等边界会暴露漏洞；把问题归咎于「token」会误导优化方向。
- **建议做法**：像代码测试一样设计边界与异常输入（正常量、超量、无关任务等），用结果反推 Prompt/Skill 是否需补全分支，而不是评价单次 token。
- **备注**：原文中「判断 token」的表述，此处按澄清结论改为检验提示词或 Skill。



##### 3.3.6 小概率场景用事后检查，不塞常驻规则

**类型**：经验

极低频、场景绑定的失败，适合任务后检查，不宜塞进常驻 Prompt。

- **现象 / 场景**：Python 中 f-string 换行与 `"-" * n` 一类乘法拼接不当，曾导致大段内容被重复刷屏；属特定写法下的小概率问题。
- **建议做法**：完成后做一次针对性 check；不要为每个小概率坑增加常驻规则，以免规则膨胀、主目标被冲淡。
- **备注**：错误形态示意（说明作用域问题即可，非完整复现）：

```python
# 错误形态示意：乘法作用域与 f-string 拼接不当，可能导致大段内容被重复
f"content\n\n"
f"-" * 30 + f"\n\ncontent"
```



##### 3.3.7 格式转换：外层勿套代码块；可脚本+AI 润色

**类型**：经验

长文转 Markdown 时外层勿再套代码块；HTML→md 可脚本先行再 AI 润色；纯靠 AI 转 PDF 质量差。

- **现象 / 场景**：多模型在长内容转 md 时，时而整段进代码块、时而直接输出，格式混乱；HTML 结构适合机械抽取；PDF 版式复杂，纯模型转换结果往往不可用。
- **建议做法**：要求「直接输出内容，最外层不要套代码块」；HTML→md 先写脚本抽取，再让 AI 补代码块与样式；PDF 优先可靠抽取链路，不依赖单次纯 AI 转换。
- **备注**：格式转换类任务通常不需要过深的推理，重点是输出形态稳定。



##### 3.3.8 文科资料整理慎用 AI 编造与脚本替换

**类型**：经验

文科资料易被模型脱离原文编造；多轮正则/脚本替换易误匹配且难回滚。

- **现象 / 场景**：让 AI 整理人文类材料时，易补写原文没有的表述；用 Agent 写脚本做多轮批量替换时，匹配过宽会改错，且难以逐步回退。
- **建议做法**：以原文为准，禁止无依据扩写；需要批量改写时优先可审阅、可回滚的流程，慎用多轮盲目正则替换；重要材料先备份再改。
