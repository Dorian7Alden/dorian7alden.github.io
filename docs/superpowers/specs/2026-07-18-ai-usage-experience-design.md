### 1. 背景与目标



#### 1.1 背景

`archives/AI/AI感想.md` 记录了日常使用 AI 工具时的零散感想、机制观察、踩坑、产品构想与待办，约 600 行，以空行分隔的碎片为主，部分条目仅有关键词或半截句子，不便查阅与续写。



#### 1.2 目标

将碎片整理为**结构化经验库**：按类型分章、按主题分节，条目结论先行，书面工整，便于长期增补与检索。



#### 1.3 成功标准

1. 新建终稿文件，原文 `AI感想.md` 保留不动。  
2. 原则 / 经验 / 构想 / 待办边界清晰，构想一律标「未验证」。  
3. 已在对话中澄清的含糊条目写入对应章节；不编造未确认细节。  
4. 附录提供条目与原文的对照表。  
5. 文风工整偏书面，去掉过激口语，保留明确判断。  
6. 与 `01-AI 发展对大学生的影响.md` 完全独立，互不改写。



#### 1.4 非目标

- 不修改 `AI感想.md` 正文。  
- 不修改 `01-AI 发展对大学生的影响.md`。  
- 不强制更新 `archives/AI/README.md`（可作为实现后的可选跟进）。  
- 不变更仓库顶层目录结构。  
- 不做网站构建或 `main` 分支相关操作。  
- 不把未验证构想写成已验证经验。

### 3. 整理策略（方案 A）

按**内容类型**分章，章内再按主题分节：

1. **使用原则与方法论** — 可反复套用的判断标准  
2. **机制与工具经验** — 已观察现象 + 可执行建议  
3. **产品与工作流构想** — 未验证点子  
4. **待办与学习清单** — 要做 / 要学 / 要收集  
5. **附录** — 整理说明 + 原文对照  

同一内容跨类时：以主类型入章，文内一句交叉引用。

### 5. 统一条目格式



#### 5.1 类型标签

| 标签 | 含义 | 主落章 |
|------|------|--------|
| `原则` | 可反复套用的判断标准 | 第 2 章 |
| `经验` | 机制观察 / 踩坑 + 建议 | 第 3 章 |
| `构想` | 未验证产品或工作流点子 | 第 4 章 |
| `待办` | 要做、要学、要收集 | 第 5 章 |



#### 5.2 单条结构

```markdown
#### 条目标题

**类型**：原则 | 经验 | 构想 | 待办  
**状态**：（构想写「未验证」；待办写「未开始」等；原则/经验可省略）

一句话结论。

- **现象 / 场景**：（可选）
- **原因 / 机制**：（可选）
- **建议做法**：（原则与经验尽量有）
- **备注**：（可选）
```



#### 5.3 写法约定

1. 结论先行。  
2. 书面语气；去掉脏话与过激措辞，保留明确立场。  
3. 经验条尽量落到「做什么 / 不做什么」。  
4. 构想必标「未验证」。  
5. 不编造：原文与对话未确认的细节不写。  
6. 必要时代码只保留最小示例。  
7. 图片：有说明价值则保留并配文字；无法复述的可只留文字结论。  
8. 标题层级遵循仓库规范：文档题 `##`，内容从 `###` 起；终稿条目标题用 `####`。  
9. 标题与段落上下文空一行。



### 6. 章节条目清单



#### 6.1 第 2 章 使用原则与方法论

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 2.1 | AI 不能替代系统设计 | 一句话描述易制造「开发变容易」的错觉；缺整体设计时逻辑脆弱、技术债高。 |
| 2.2 | Vibe Coding 宜先探坑再正式设计 | 可先快速试做，把暴露问题作为正式设计输入，而非跳过设计当成品。 |
| 2.3 | 人必须监管与决策 | 不追求 AI 不间断自动交付产品；关键决策与验收在人侧。 |
| 2.4 | 多次小任务优于一次大包 | 长任务易偏航、易「偷懒」；拆成可验收小步更稳。 |
| 2.5 | 质量优先于「能跑多久」 | 好 Agent 标准是符合预期、可维护、成本可控，而非长时间空转。 |
| 2.6 | 资料与知识库重于反复调 Prompt | 提示词难复用；可复用的是规范、范例与知识库。 |
| 2.7 | 看懂 ≠ 会用 ≠ 能讲懂 | AI 讲解易造成学会错觉；能讲清、能跑通才算内化。 |
| 2.8 | 用陈述补上下文，不用反问纠错 | 「难道不该是…」仍在逼模型猜意图；应明确补充要求与背景。 |
| 2.9 | 正向说明优先于堆反向约束 | 尽量写期望行为；过多「不要…」易被淹没。 |
| 2.10 | 先跑通再优化 | 初期以可运行为主，再迭代结构与质量。 |
| 2.11 | 执行要有思维链与原因 | 每个关键操作应能说明为何这样做（「该这么做」）。 |
| 2.12 | 先收集已知条件再切入 | 收集条件 → 找切入点 → 分析 → 澄清 → 方案 → 执行（「该这么做」）。 |

说明：2.11、2.12 由原构想清单下沉，按用户确认记为原则/方法，不放第 4 章。



#### 6.2 第 3 章 机制与工具经验



##### 3.1 上下文与记忆

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 3.1.1 | 上下文永远不完整 | 未写出的默认理解与动态状态（如 Git）模型不会自动知道。 |
| 3.1.2 | 网页对话 vs Agent 工具的上下文形态 | 网页端近似多轮 Q/A 拼接；Agent 工具还含思考、工具调用与命令结果，管理更复杂。 |
| 3.1.3 | 摘要替换上下文，原始记录另存 | 进上下文的是摘要；原始聊天宜保留，避免只靠不可逆压缩。 |
| 3.1.4 | 生成内容有「缓存变量」效应 | 用户手改文件后若未让 AI 重读，后续可能仍基于旧生成内容。 |
| 3.1.5 | 主会话宜委派，细节交给 Sub-agent | 上下文紧张时，主对话只分发与验收。 |



##### 3.2 任务委派与 Agent 结构

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 3.2.1 | 分层委派，上层只看摘要 | Boss 发目标与约束并验收；Worker 执行并回摘要。 |
| 3.2.2 | 不同任务用不同策略 | 不宜一套策略打天下。 |
| 3.2.3 | 执行前先对齐任务理解 | 开工前简短复述目标与步骤。 |
| 3.2.4 | Agent 默认被动，需主动补上下文 | 未读全约束就开干会导致偏差。 |

说明：原文「3 层 agent」不机械写成固定三层，而写成**分层委派 / 上下文隔离**；三层结构可作为可选延伸备注。



##### 3.3 规则、Skill 与提示词

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 3.3.1 | 规则会衰减，且会与 Skill 冲突 | 长上下文或强 Skill（如自动 commit 流程）可能冲掉既有约束。 |
| 3.3.2 | 规则有例外，要写清优先级 | 例外需说明原因，并保留决策记录。 |
| 3.3.3 | Skill 宜通用，勿绑定单次会话状态 | 过贴瞬时仓库状态，换会话即失效。 |
| 3.3.4 | Skill 要区分常量与变量 | 明确固定项与可变输入，并做效果测试。 |
| 3.3.5 | 用边界用例检验 Prompt/Skill | 类似「1 杯 / 99 杯 / 蛋炒饭」测覆盖与稳定性。 |
| 3.3.6 | 小概率场景用事后检查，不塞常驻规则 | 如 Python f-string 与 `"-" * n` 拼接导致刷屏；常驻规则性价比低。 |
| 3.3.7 | 格式转换：外层勿套代码块；可脚本+AI 润色 | 长文转 MD 易乱；HTML→md 可脚本先行；纯靠 AI 转 PDF 质量差。 |
| 3.3.8 | 文科资料整理慎用 AI 编造与脚本替换 | 易脱离原文；多轮正则替换难回滚、易越改越乱。 |



##### 3.4 Claude Code 与配置管理

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 3.4.1 | ignore 的文件也可能被插件强行纳入 Git | 某些插件/流程会把工作记录写进仓库。 |
| 3.4.2 | 仓库 ignore 配置文件会导致多分支配置混乱 | 忽略 Claude 相关配置后，分支间配置不一致。 |
| 3.4.3 | CLAUDE.md 放稳定说明，不放具体任务清单 | 任务另文件；CLAUDE.md 侧重目录与固定约定。 |
| 3.4.4 | 配置集中管理，且按项目区分 | 配置放清晰目录；**项目级**，不同项目不同要求。 |
| 3.4.5 | Memory 与规范采用项目级 | **禁止依赖全局统一规范**；Memory/约定按项目维护。 |



##### 3.5 编码、文档与维护策略

| ID | 条目标题 | 一句话结论 |
|----|----------|------------|
| 3.5.1 | AI 偏事后修 bug，缺预防式设计 | 人要补健壮性、边界与预防。 |
| 3.5.2 | 改代码前要能定位结构与标识 | 说不清改哪、无稳定路径/id 时结果不稳。 |
| 3.5.3 | 数据获取类逻辑易前后不一致 | 如爬虫阶段与数据可用性需显式说明。 |
| 3.5.4 | 分散维护优于一次性大重构 | 碰到文件再顺手维护；区分通用规范与特殊要求。 |
| 3.5.5 | 维护宜挂在读取任务上 | 少做纯维护会话；读文档办事时对照清单维护。 |
| 3.5.6 | 文档有过时风险，关键结论需二次确认 | 尤其规范、接口、配置类。 |
| 3.5.7 | 长文本任务易忘规则：先备份再改 | 编辑前 Copy 备份。 |
| 3.5.8 | AI 不主动关联相关文件与 Git 历史 | 协作上下文需人指定。 |
| 3.5.9 | 前端可先 Demo 组件、先设计后实现 | 按组件搭测试页，先 UI 结构再实现。 |

### 7. 对话中已澄清的关键语义（实现时必须遵守）
