# 第1章 导言
## 1.1 计算机与软件
### 1.1.1 通常的系统软件
+ **核心作用**：为应用程序员提供**硬件资源和低层软件的抽象接口**，隐藏硬件细节（如磁盘读写、设备控制）。
+ **关键分类**： 
    - 操作系统（OS）：最底层系统软件，直接操作硬件，管理资源共享与隔离。
    - 其他系统软件（如编译器、数据库、窗口系统）：基于 OS 接口构建，依赖 OS 的可信操作。
+ **层级关系**：硬件 → OS（系统调用接口）→ 其他系统软件（API）→ 应用软件 → 人机界面（用户直接使用）。

### 1.1.2 资源抽象
+ **定义**：将复杂的物理资源（如磁盘、键盘）封装为简单的逻辑接口，让程序员无需关注硬件细节。
+ **核心目的**：简化编程，统一资源操作方式（不同硬件用相同接口）。
+ **示例**： 
    - 磁盘抽象：用`fileID`（文件标识符）代表磁盘，通过 C 语言`stdio`库的`fprintf(fileID, "%d", datum)`操作磁盘，无需了解磁盘磁道、扇区细节。
    - 磁带抽象：与磁盘使用相同的抽象接口（如`read()`/`write()`），仅底层实现不同。

### 1.1.3 资源共享
+ **两类共享场景**： 
    1. **透明共享**：用户 / 程序员无感知，由 OS 自动管理（如处理器、内存的共享）。
    2. **显式共享**：需程序员主动协调，OS 提供共享机制（如两个进程共享雇员工时文件）。
+ **共享的关键前提**：OS 需同时保证**资源隔离**（防止未授权访问，如进程不能访问其他进程内存）和**合法共享授权**（如进程间共享计算结果）

### 1.1.4 虚拟机和透明资源共享
+ **虚拟机（VM）定义**：OS 为每个进程模拟的 “私有计算机”，进程看似独占硬件，实际由 OS 调度资源共享。
+ **实现共享的两种核心技术**：

| **共享技术** | **适用资源** | **原理** |
| --- | --- | --- |
| 时分复用 | 处理器 | 进程轮流使用处理器（时间片），如 3 个进程分时共享 1 个 CPU |
| 空分复用 | 内存 | 将内存分割为多个块，分配给不同进程，如进程 A 用内存块 1、进程 B 用内存块 2 |


+ **多道程序设计（关键技术）**：
    - 定义：通过 “时分复用处理器 + 空分复用内存”，让多个进程并发执行。
    - 核心价值：提升资源利用率，减少总执行时间（理想情况下，N 个进程总时间 = 最长进程时间；最差 = 各进程时间总和）。
    - 示例：进程 A 执行 I/O 时，OS 将 CPU 分配给进程 B，实现 CPU 与 I/O 并行。

### 1.1.5 显示资源共享
+ **核心要求**： 
    1. OS 提供**资源隔离机制**（如内存隔离：进程只能访问自己的内存块）。
    2. OS 提供**合法共享机制**（如文件共享：授权进程可读写同一文件）。
+ **关键概念：可信软件**： 
    - 定义：OS 内核是可信软件，能严格执行资源隔离策略，避免因漏洞导致隔离失效（如恶意进程篡改其他进程数据）。
    - 重要性：OS 的正确性依赖可信软件，其他软件（应用、工具）均为不可信软件，依赖 OS 保证安全。

## 1.2 操作系统策略
### 1.2.1 批处理系统
+ **用户观点**：非交互式，用户需提前准备 “作业”（程序 + 数据 + 控制命令），提交后等待批量处理结果（无实时交互）。
+ **核心技术：假脱机（Spooling）**： 
    - 原理：用磁盘作为中间缓存，将多个作业先读入磁盘 “输入池”，OS 按顺序从输入池调度作业执行，结果写入 “输出池”。
    - 示例：企业每月生成发货单，多个作业（计算销售、确认发票、更新账户）批量处理，无需用户干预。
+ **现代价值**：非交互式任务仍适用（如打印薪水单、分析地震数据），但不再是主流 OS 策略。

### 1.2.4 分时系统
+ **用户观点**：交互式，用户通过 “登录” 建立会话，实时输入命令、查看结果（如编辑文件、编译程序），感觉独占一台 “慢一点的计算机”。
+ **核心技术**： 
    - 基于多道程序设计，为每个用户进程分配时间片，保证响应时间短（不超载时）。
    - 公平的处理器共享策略：避免单个进程独占 CPU。
+ **示例：UNIX 分时系统**： 
    - 20 世纪 80 年代中期成为主流，支持多用户同时登录，每个用户通过 shell（命令解释器）交互，OS 分时调度进程。
+ **对现代 OS 的贡献**：引入 “用户 - OS 实时交互”，推动进程保护与安全（多用户共享需防止权限越界）。

### 1.2.7 个人计算机与工作站
+ **硬件背景**：1977 年 Apple II、1981 年 IBM PC 问世，早期 PC 硬件简单，无多道程序设计能力（一次仅执行一个程序）。
+ **核心技术**： 
    - 设备抽象软件：Apple 的 “工具箱”、IBM 的 BIOS（存储在 ROM 中，掉电不丢失），提供磁盘、键盘等设备的抽象接口。
    - 工作站的突破：1982 年 Sun 等厂商推出工作站，支持多道程序设计（采用 UNIX），硬件资源充足（如更大内存、更快 CPU）。
+ **演化结果**：1990 年后 PC 硬件升级，与工作站差异缩小，OS 统一支持多道程序设计（如 Windows 95/NT、Linux）。
+ **用户观点**：PC / 工作站为 “个人工具”（如文字处理、编程），用户独占设备，OS 需简化操作（如图形界面）、提升单用户体验。

### 1.2.11 嵌入式系统
+ **应用场景**：嵌入到硬件设备中的 OS（如智能手表、汽车控制器、核反应堆监控），需满足 “实时性、低功耗、小体积”。
+ **核心技术**： 
    - 实时调度：保证关键任务在 “硬期限” 内完成（如反应堆温度超标时，需在 100ms 内发送降温信号）。
    - 低资源消耗：OS 占用内存 / CPU 少，部分嵌入式系统仅运行单个应用（无需多进程共享）。
    - 电源管理：支持设备动态掉电（如屏幕、传感器空闲时断电），延长电池寿命。
+ **示例：VxWorks**： 
    - 模块化微内核（Wind Microkernel），可配置组件，适用于实时场景（如航空航天、工业控制）。
+ **对现代 OS 的贡献**：推动 “实时技术” 发展，部分实时机制被用于通用 OS（如 QoS：服务质量保证，如网络传输低延迟）。

### 1.2.15 小型通信计算机
+ **应用场景**：手持设备（如掌上电脑、机顶盒、车载电脑），需 “便携性、低功耗、网络连接”。
+ **示例：Windows CE（Pocket PC）**： 
    - 核心特点：可配置模块化（无需重新编译即可组合组件），实现 Win32 API 子集（约 1/4），支持硬件抽象层（OAL），适配不同硬件（如 ARM、x86 处理器）。
    - 限制：无兼容性负担（无需支持 MS-DOS/Win16 应用），但功能精简（无桌面 OS 的完整图形 / 网络支持）。

### 1.2.18 网络
+ **核心需求**：多台计算机通过网络互连，OS 需支持 “远程资源共享”（如访问另一台机器的文件、打印机）。
+ **技术基础**：基于之前的 OS 策略（多道程序设计、进程管理），增加 “网络协议”（如 TCP/IP），实现跨机器通信。

### 1.2.19 现代操作系统的起源
+ **演化路径**：单用户计算机 → 批处理系统（提升利用率）→ 分时系统（增加交互性）→ 个人机 / 工作站（单用户体验）→ 嵌入式 / 小型通信计算机（专用场景）→ 网络 OS（分布式共享）。
+ **现代 OS 的核心特征**：融合多策略优势，支持多进程 / 线程、虚拟内存、分布式共享、安全机制（如加密）、实时调度（部分场景）。

## 1.3 核心小结
1. **OS 的本质**：通过 “抽象”（隐藏硬件细节，如文件抽象磁盘）和 “共享”（时分 / 空分复用资源），为进程创建虚拟机环境，协调资源使用。
2. **关键概念关联**： 
    - 多道程序设计是 “虚拟机并发” 的基础，依赖时分（CPU）和空分（内存）复用。
    - 可信软件（OS 内核）是 “资源隔离与安全” 的保障。
3. **OS 演化逻辑**：需求驱动（从 “用满硬件” 到 “用户体验、专用场景”），技术继承（如分时系统继承多道程序设计，嵌入式系统继承实时调度）。
4. **后续衔接**：本章为 OS 概念铺垫，下一章将深入 “OS 提供的资源抽象模型（进程、线程、文件）” 及如何使用这些抽象。

# 第2章 使用操作系统
## 2.1 程序员看到的虚拟机
虚拟机是 OS 为程序员构建的 “逻辑计算环境”，核心包含 “计算单元”（进程 / 线程）和 “资源”（文件、内存等），本章先聚焦计算单元的两种核心模式。

### 2.1.1 顺序计算
+ **定义**：程序按 “逐条指令、单一控制流” 执行，符合传统算法逻辑（如排序、计算），对应 “经典进程” 模型。
+ **执行流程**（）： 
    1. 编译器编译源码为可执行文件（如 UNIX 的`a.out`）；
    2. 加载程序到内存，OS 为其分配资源（内存、文件句柄）；
    3. 从`main()`入口点启动执行，按控制流（顺序、分支、循环）执行；
    4. 执行完成（隐式到最后一条指令，或显式调用`exit()`），释放资源。
+ **关键抽象：经典进程**（）： 
    - 构成：包含 “可执行二进制程序 + 数据 + 资源（如打开的文件）+ 执行引擎”；
    - 执行引擎：OS 维护的内部数据结构（如进程状态、程序计数器）+ 运行时栈（局部变量、函数返回地址），是进程的 “活动部分”。
+ **OS 调度特点**：OS 通过 “时分复用” 让多个顺序进程并发执行（如进程 A 执行 10ms 后切换到进程 B），但程序员感知不到切换，仅认为自己的程序在独占 CPU。

### 2.1.2 多线程计算
+ **定义**：一个进程内包含多个 “独立控制流”（线程），共享进程的程序、数据和资源，仅私有线程栈和状态，对应 “现代进程” 模型。
+ **类比理解**（）： 
    - 进程 =“会计室”（提供发票、购买订单等共享资源）；
    - 线程 =“会计师”（独立处理发票，共享会计室的资源，有自己的工作记录（栈））。
+ **核心优势**： 
    - 并发效率高：线程切换无需拷贝地址空间（进程切换需拷贝）；
    - 资源共享便捷：同一进程的线程直接访问全局数据，无需额外通信机制。
+ **实现示例**（）： 
    - Java 通过`Thread`类支持多线程：定义`Thread`子类（如`MyThread`），创建实例即生成新线程，可直接访问进程的全局数据；
    - 注意：早期 OS（如 Linux 2.0）仅支持经典进程，多线程需通过 “用户态线程库” 模拟（如 Mach C 线程包），但存在 “一个线程阻塞则全进程阻塞” 的缺陷，现代 OS（如 Windows、Linux 2.2+）均支持内核级线程。

## 2.2 资源：虚拟机的 “被动组件”
资源是进程 / 线程执行所需的 “虚拟机部件”（物理资源如 CPU、内存，抽象资源如文件、管道），OS 通过统一接口管理资源，核心特点是 “显式请求、阻塞等待”（资源不可用时，进程 / 线程挂起）。

### 2.2.1 使用文件（最核心的抽象资源）
文件是 “持久化存储的字节流抽象”，不同 OS 的文件操作接口逻辑一致，仅语法差异。

**1. POSIX 文件（UNIX/Linux）**

+ **核心接口**：`open()`（打开文件，返回文件描述符）→ `read()`/`write()`（读写字节流）→ `close()`（关闭文件）；
+ **示例代码逻辑**（）：

```c
#include <fcntl.h>int main() {
  int inFile = open("in_test", O_RDONLY); // 只读打开输入文件
  int outFile = open("out_test", O_WRONLY); // 只写打开输出文件
  char c;
  while (read(inFile, &c, 1) > 0) { // 逐字节读入
    write(outFile, &c, 1); // 逐字节写出
  }
  close(inFile); close(outFile);
}
```

+ **关键特点**：文件指针隐式维护（读写后自动偏移），支持 “随机访问”（通过`lseek()`调整指针位置）。

**2. Windows 文件**

+ **核心接口**：`CreateFile()`（打开 / 创建文件，返回句柄`HANDLE`）→ `ReadFile()`/`WriteFile()`（读写块数据）→ `CloseHandle()`（关闭文件）；
+ **关键特点**（）： 
    - 64 位文件指针：支持大文件（超过 4GB）；
    - 句柄机制：`HANDLE`指向 OS 内部数据结构（记录文件指针、权限等），而非直接操作文件；
    - 示例差异：Windows 倾向 “块读写”（如每次读`BUFFER_LEN`字节），而非 UNIX 的 “字节读写”，效率更高。

### 2.2.2 使用其他资源
+ **核心原则**：OS 尽量统一资源接口，让程序员无需区分资源类型（如键盘、显示器、管道均可用类似文件的接口操作）。
+ **典型示例**（）： 
    - UNIX 的 “设备即文件”：键盘对应`/dev/tty`、显示器对应`/dev/console`，可通过`read()`/`write()`操作，与文件接口一致；
    - 管道（进程间通信资源）：通过`pipe()`创建，用`read()`/`write()`传递数据，抽象为 “内存中的字节流文件”。
+ **资源请求逻辑**：进程需先通过`open()`等调用 “申请资源”，资源不可用时（如文件被独占写），进程进入阻塞状态，直到资源释放。

## 2.3 进程和线程：虚拟机的 “活动组件”
进程是 “计算的静态框架”（程序 + 数据 + 资源），线程是 “计算的动态单元”（执行引擎），二者的关系是现代 OS 的核心设计。

### 2.3.1 核心定义与区别
| **维度** | **进程（现代）** | **线程** |
| --- | --- | --- |
| 地址空间 | 独立（每个进程有专属地址空间） | 共享（同一进程的线程共享地址空间） |
| 资源 | 独占（如文件句柄、内存块） | 共享（进程的资源对线程可见） |
| 执行单元 | 无（需包含至少一个线程才能执行） | 有（独立的程序计数器、栈、状态） |
| 切换开销 | 大（需拷贝地址空间、资源表） | 小（仅需切换线程栈和状态） |
| 示例（Windows） | `CreateProcess()`<br/>创建 | `CreateThread()`<br/>创建 |


+ **经典进程 vs 现代进程**： 
    - 经典进程（如早期 UNIX）：“进程 = 线程”，每个进程仅一个执行单元，无独立线程概念；
    - 现代进程（如 Windows、Linux）：进程是 “资源容器”，线程是 “执行单元”，一个进程可包含多个线程。

### 2.3.2 进程 / 线程的创建机制
**1. 历史模型：FORK ()、JOIN ()、QUIT ()**

+ 起源：1963 年 Conway 提出，用于创建 “单线程进程家族”（）；
+ 核心语义： 
    - `FORK(label)`：父进程创建子进程，子进程从`label`处开始执行，父进程继续执行后续指令，二者共享地址空间（类似现代线程）；
    - `JOIN(count)`：多个进程合并，`count`为共享变量，进程执行`JOIN()`时`count--`，最后一个进程执行完后唤醒其他进程；
    - `QUIT()`：进程终止，释放资源。
+ 局限：仅支持单线程，无法满足现代多线程需求，仅作为 “进程创建思想的起源”。

**2. 经典进程创建（UNIX fork ()）**

+ **核心逻辑**（）： 
    - 子进程是父进程的 “地址空间拷贝”：代码段、数据段、栈段均拷贝，父进程与子进程地址空间独立（修改子进程变量不影响父进程）；
    - `fork()`返回值：父进程得到子进程 PID（进程 ID），子进程得到 0，用于区分父子进程；
    - 示例场景：UNIX shell 创建子进程执行命令（如`ls`），父进程通过`wait()`等待子进程结束。

**3. 现代进程与线程创建（Windows）**

+ **进程创建**（）： 
    - `CreateProcess()`：先创建 “现代进程”（分配地址空间、资源），再自动创建 “基线程”（执行`main()`入口），确保进程可立即执行；
    - 差异：与 UNIX `fork()`不同，Windows 子进程不拷贝父进程地址空间，而是加载新程序（如`notepad.exe`），更适合 “执行不同程序” 的场景。
+ **线程创建**（）： 
    - `CreateThread()`：在已有进程内创建子线程，需指定 “线程函数入口”（如`ThreadFunc`）和 “参数”，子线程共享进程的程序、数据；
    - 关键参数：`lpStartAddress`（线程函数地址）、`lpParameter`（传递给线程的参数），线程有独立栈（大小由`dwStackSize`指定，0 为默认）。

## 2.4 并发程序的编写
### 2.4.1 UNIX 模型：多单线程进程
+ **核心技术**：`fork()`（创建子进程）+ `execvp()`（加载新程序）+ `wait()`（等待子进程结束）；
+ **示例：模拟 shell 的**`**launch**`**程序**（）： 
    1. 功能：从文件`launch_set`读取命令（如`ls -l`、`date`），为每个命令创建子进程执行；
    2. 关键步骤： 
        * 解析命令：`parseCommand()`将命令行拆分为`argv`数组（如`ls -l`拆为`argv[0]="ls", argv[1]="-l"`）；
        * 创建子进程：`fork()`生成子进程，子进程调用`execvp(command.name, command.argv)`加载并执行命令；
        * 父进程等待：`wait(&status)`等待所有子进程结束，避免 “僵尸进程”。
+ **关键注意**：`execvp()`会 “替换子进程的地址空间”（加载新程序），因此需先`fork()`再`execvp()`，若先`execvp()`，父进程会被新程序替换，无法继续创建其他子进程。

### 2.4.2 Windows 模型：多进程与多线程
+ **进程创建示例**（）：

```c
STARTUPINFO startInfo;
PROCESS_INFORMATION procInfo;
ZeroMemory(&startInfo, sizeof(startInfo));
startInfo.cb = sizeof(startInfo);
// 创建子进程执行notepad.exe，打开temp.txt
CreateProcess(NULL, "C:\\\\WINNT\\\\SYSTEM32\\\\NOTEPAD.EXE temp.txt",
              NULL, NULL, FALSE, CREATE_NEW_CONSOLE, NULL, NULL,
              &startInfo, &procInfo);
CloseHandle(procInfo.hThread); // 关闭线程句柄
CloseHandle(procInfo.hProcess); // 关闭进程句柄
```

    - 关键参数：`CREATE_NEW_CONSOLE`为子进程创建独立控制台窗口，避免与父进程混淆。
+ **线程创建注意**（）： 
    - 线程函数原型：必须符合`DWORD WINAPI ThreadFunc(LPVOID lpParam)`，否则编译报错；
    - `_beginthreadex()`替代`CreateThread()`：若使用 C 运行时库（如`printf()`），需用`_beginthreadex()`（而非`CreateThread()`），避免 “线程安全问题”（如全局变量`errno`被覆盖）。

## 2.5 对象：OS 的 “抽象扩展机制”
+ **核心思想**：对象是 “封装了数据和操作的自治单元”，用于简化 OS 的模块化设计和资源管理。
+ **OS 中的对象应用**（）： 
    - Windows NT 内核：将 “线程、进程、文件” 设计为对象，通过 “对象管理器” 统一管理，支持 “继承”（如`dispatcher`对象扩展为线程对象）；
    - 优势：隐藏实现细节，仅暴露接口（如线程对象的`ResumeThread()`、`SuspendThread()`），便于扩展和维护。
+ **局限**：纯面向对象 OS（如 Sun 的 Spring OS）因 “性能开销大” 未普及，现代 OS 多采用 “混合模型”（用 C 实现对象思想，而非纯 OOP 语言）。

## 2.6 核心小结
1. **虚拟机的构成**：由 “静态资源”（文件、内存、设备）和 “动态单元”（进程 / 线程）组成，OS 通过统一接口（如文件接口、系统调用）让程序员无需关注硬件细节。
2. **进程与线程的核心关系**：进程是 “资源容器”，线程是 “执行单元”，现代 OS 通过 “多线程进程” 提升并发效率（减少切换开销）、简化资源共享。
3. **不同 OS 的实现差异**： 
    - UNIX：基于 “经典进程” 演化，支持`fork()`拷贝地址空间，适合 “父子进程共享数据” 场景；
    - Windows：原生支持 “现代进程 + 线程”，通过`CreateProcess()`/`CreateThread()`分离创建，适合 “多任务、多线程协作” 场景。
4. **实践关键**：编写并发程序需关注 “资源共享”（如线程共享全局变量需同步）和 “进程隔离”（如 UNIX 子进程修改数据不影响父进程）。

## 2.7 实验提示
**实验 2.1：简单 shell（UNIX）**

+ **核心任务**：实现交互式命令解释器，支持用户输入命令（如`ls`、`cd`），创建子进程执行；
+ **关键技术**（）： 
    - 命令解析：拆分命令行为`argv`数组，处理`PATH`环境变量（查找命令所在目录，如`ls`在`/bin`下）；
    - `fork()`+`execv()`：`execv()`需指定命令的绝对路径（如`/bin/ls`），而非`execvp()`的 “自动查找”；
    - 内置命令：`cd`（切换目录）需在 shell 进程内执行（不能创建子进程，否则子进程切换后父进程目录不变）。

**实验 2.2：多线程应用（Windows）**

+ **核心任务**：编写`mthread.exe`，接收参数`N`，创建`N`个线程执行 “模拟工作”（如计算幂函数）；
+ **关键技术**（）： 
    - 线程同步：用全局变量`runFlag`控制线程终止（`runFlag=FALSE`时所有线程退出）；
    - `Sleep()`的使用：创建线程后调用`Sleep(100)`，让新线程有机会运行，避免主线程独占 CPU；
    - 线程函数：需符合`DWORD WINAPI ThreadFunc(LPVOID)`，参数通过`LPVOID`传递（如线程编号）。
